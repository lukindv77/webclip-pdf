# История функционала и причины изменений

История составлена по ходу разработки. Для ранних прототипов важнее смысл решения, чем точный diff исходников.

## WIP 0.9.9 — переключение URL / сайт / весь журнал в одной journal-tab

- `mode=all` сохраняет session source-context при запуске с HTTP(S)-страницы, но не использует его для фильтрации полного списка;
- popup на `journal.html` восстанавливает исходный web-context по `contextId`;
- `sourceTabId` (контекст фильтра) отделён от `anchorTabId` (позиция новой вкладки справа от текущей);
- исправлена ситуация, когда после открытия журнала в новой extension-вкладке остальные виды журнала становились недоступны из-за потери исходного URL.

## 0.9.7 — журнал полностью отвязан от origin активной вкладки

### Изменено
- все страницы журнала открываются только через service worker (`WEBCLIP_OPEN_JOURNAL_PAGE`), а не напрямую из action popup;
- `sourceTabId` и `sourceUrl` больше не передаются в URL `journal.html`; вместо этого service worker сохраняет краткоживущий контекст в `chrome.storage.session` и передаёт странице только одноразовый `contextId`;
- режим `Весь журнал` при чтении записей не использует URL/домен исходной вкладки; исходный контекст нужен только для перехода к `Текущий URL`/`Текущий сайт` и применения snapshot;
- чтение списка имеет два независимых источника: прямой IndexedDB и service worker; интерфейс выбирает более полную выборку и пишет расхождение в консоль;
- добавлен регрессионный тест: число записей `Весь журнал` должно быть одинаковым при запуске из `chrome://newtab/`, уже открытой `https://`-вкладки и после навигации пустой вкладки на URL.

### Причина
В 0.9.4–0.9.6 пользователь воспроизвёл зависимость: полный журнал был виден при запуске с новой пустой вкладки, но становился пустым, если активной была обычная веб-страница. Поскольку сами записи и badge service worker оставались корректными, контекст активной вкладки исключён из жизненного цикла полного журнала.

## 0.9.4 — строгий индикатор Яндекс Диска и улучшение журнала

### Изменено
- цвет и badge иконки текущего URL считаются только по полностью успешным операциям `destination=yandex`; локальные скачивания PDF не влияют на индикатор;
- локальные скачивания остаются полноценными строками журнала и явно маркируются режимом `Файл`; успешные remote-операции — `Яндекс Диск`;
- кнопки `Текущий URL`, `Текущий сайт`, `Весь журнал` имеют явное активное состояние;
- фильтр общего журнала по доменам закрыт по умолчанию, базовые домены раскрываются независимо, добавлен поиск по домену;
- после изменения IndexedDB журнал отправляет live-событие, открытая страница журнала автоматически перечитывает данные;
- при открытии журнала контекст исходной вкладки повторно уточняется через `sourceTabId`, что устраняет ситуацию, когда актуальные записи становились видны только после открытия/переключения вкладки.

### Причина
Пользователь уточнил, что индикатор должен отражать именно подтверждённый удалённый архив на Яндекс Диске, а не факт локального формирования PDF. Также журнал должен быть визуально однозначным, не требовать переоткрытия вкладки и оставаться удобным при большом числе доменов.

## 0.1.x — первый PDF WebClip

### Добавлено
- выбор одной/нескольких DOM-областей;
- формирование PDF через Chromium `Page.printToPDF`;
- стандартное скачивание Chrome;
- заголовок PDF с адресом сайта, URL, Title, локальной датой/временем;
- кликабельные ссылки;
- безопасное имя файла.

### Причина
Нужен минимальный тестовый WebClip без сервера и внешней базы.

## 0.2.x — модель «Включены/Исключены» и укрупнение областей «Включены»

### Изменено
- отказ от простой модели «только независимые области»;
- введены области «Включены» и «Исключены»;
- выбор более крупного родителя поглощает дочерние области «Включены»;
- области «Исключены» сохраняются при укрупнении областей «Включены», если остаются валидно вложенными;
- добавлен автоматический выбор основного контента.

### Причина
Пользователю требуется сохранять крупный блок статьи, но вырезать отдельные вложенные элементы, а также удобно расширять выбор вверх по DOM.

## 0.3.0 — реклама только как подсказка

### Изменено
Автоматическое обнаружение рекламы больше не исключает блоки само. Добавлена функция подсветки кандидатов.

### Причина
Пользователь прямо потребовал, чтобы решение об исключении всегда оставалось за ним. Эвристика не должна разрушать архивную копию.

## 0.4.0 — раскрытие спойлеров

### Добавлено
Попытка раскрыть `details`, `aria-expanded/aria-controls`, collapse/accordion и распространённую spoiler-разметку внутри областей «Включены».

### Изменено
Раскрытое состояние после PDF не откатывается.

### Причина
Скрытый контент должен попадать в архивную копию, а пользователь разрешил оставить страницу в раскрытом состоянии.

## 0.5.0 — Яндекс Диск

### Добавлено
- второй способ сохранения: Яндекс Диск;
- корневая папка;
- вложенность по домену;
- REST API upload;
- окна успеха/ошибки;
- настройки подключения.

### Причина
Нужен удалённый архив, доступный независимо от локальной папки загрузок.

## 0.6.0 — фиксированный Redirect URI Яндекс

### Изменено
Авторизация перестроена под фиксированный `https://oauth.yandex.ru/verification_code` и Authorization Code + PKCE.

### Причина
Для выбранного типа приложения Яндекс не позволял менять Redirect URI. Использование `chrome.identity` callback стало неподходящим.

## 0.6.1 — встроенная инструкция Яндекс OAuth

### Добавлено
Отдельная офлайн-страница инструкции, вызываемая кнопкой из popup и настроек.

### Причина
Авторизация требует нескольких ручных шагов и регистрации приложения; пользователь попросил подробную встроенную инструкцию.

## 0.6.2 — имя Яндекс-файла

### Изменено
Имя для Яндекс Диска приведено к порядку `Title + домен + дата/время + расширение`.

### Причина

## 0.6.3 — отображение версии

### Добавлено
Версия показывается в UI и читается из `manifest.json`.

### Причина
При частых ручных обновлениях расширения необходимо быстро понимать, какая сборка установлена.

## 0.6.4 — визуально критичное окно ошибки Яндекс Диска

### Изменено
Ошибка получила отдельный красный визуальный стиль, значок предупреждения, метку «Требуется действие» и явные recovery-действия.

### Причина
Пользователь потребовал, чтобы ошибка не выглядела как обычное информационное сообщение и визуально требовала разбора.

## 0.6.5 — лимит имени 100 символов

### Изменено
Единое правило имени для локального PDF и Яндекс Диска. Полная длина вместе с `.pdf` ≤ 100 символов; в первую очередь обрезается Title.

### Причина
Пользователь зафиксировал максимальную длину и обязательные части имени.

## 0.6.6 — retry того же PDF

### Добавлено
IndexedDB-кэш уже сформированного PDF.

### Изменено
После ошибки Яндекс Диска «Повторить отправку» больше не вызывает новый `Page.printToPDF`, а отправляет те же байты с тем же именем.

### Причина
Пользователь потребовал, чтобы сетевой retry не изменял содержимое/дату/имя PDF и не тратил время на повторное формирование.

## 0.7.0 — журнал и восстановление областей «Включены/Исключены»

### Добавлено
- журнал успешных локальных скачиваний и отправок на Яндекс Диск;
- фильтр всего журнала / текущего URL;
- хранение selection snapshot;
- восстановление областей «Включены/Исключены» на текущей странице;
- просмотр локаторов;
- удаление и очистка записей.

### Причина
Пользователю нужен повторяемый процесс WebClipping для тех же URL и возможность видеть, что было сохранено раньше.

### Архитектурное решение
Журнал хранится в IndexedDB, а не в папке установленного расширения: Chrome Extension не имеет общего произвольного write-доступа к каталогу своих установочных файлов.

## 0.7.2 — шаблоны выделения на уровне сайта и терминология PDF

Изменения:
- добавлен журнал текущего сайта, где сайт нормализуется до третьего уровня домена;
- области «Включены/Исключены» из записи можно применить к другому URL того же сайта;
- при cross-URL восстановлении пользователь получает предупреждение проверить результат, поскольку DOM страниц может отличаться;
- имя нового файла всегда формируется заново и не наследуется из записи журнала;
- в информационной шапке PDF подпись `Title страницы` заменена на `Название страницы`.

Причина: пользователь хочет использовать однажды настроенный шаблон выделения для типовых страниц одного сайта, а терминологию PDF сделать русскоязычной и более естественной.

## 0.8.0 — frame-aware WebClip и переносимый журнал

### Добавлено
- обход same-origin iframe/frame как отдельных DOM-контекстов;
- `framePath` в локаторах областей «Включены/Исключены»;
- восстановление шаблонов внутри iframe;
- экспорт/импорт полного журнала;
- массовая очистка домена/всего журнала с 9-значным кодом;
- резервный JSON журнала на Яндекс Диске.

### Причина
На страницах 1С:ИТС фактический документ находится внутри `iframe`, поэтому анализ только верхнего `body` некорректен. Кроме того, локальный IndexedDB-журнал нуждается в переносимом механизме восстановления.

## 0.9.2 — версионные backup, выбор файла импорта и progress UI

- Каждая ручная и фоновая резервная копия полного журнала записывается новым JSON-файлом; старые копии не удаляются.
- Структура: `Backup/Journal/MM-YYYY/WebClip_Journal_YYYY-MM-DD_HH-MM-SS-SSS.json`.
- Для upload backup используется `overwrite=false`.
- Импорт с Яндекс Диска сначала открывает отдельное окно со списком конкретных файлов; автоматический выбор последней версии удалён.
- После выбора файла сохраняется существующее опасное подтверждение с 9-значным кодом перед replace локального IndexedDB-журнала.
- Ручной backup в Journal и Options показывает блокирующее модальное окно с реальными этапами service worker: read → serialize → Yandex access → month folder → upload URL → upload → verify.
- Пока backup активен, modal нельзя закрыть и действует `beforeunload`-защита вкладки; после успеха/ошибки защита снимается.
- Контекстная команда backup журнала теперь открывает Journal с `autoBackup=1`, поэтому и этот ручной путь получает тот же progress UI вместо «тихой» фоновой операции.
- После upload выполняется GET metadata выбранного remotePath, чтобы успех означал не только HTTP upload, но и наличие файла на Диске.

**Причина:** хранение одного перезаписываемого файла не давало возможности восстановить более раннее состояние журнала и скрывало ход долгой сетевой операции от пользователя.

## 0.9.1 — исправление ручного и фонового backup журнала

### Исправлено
- В `readAllJournalEntries()` направление IndexedDB-курсора изменено с недопустимого `asc` на стандартное `next`.
- Полный журнал снова читается в возрастающем порядке `createdAt`, поэтому «Создать резервную копию сейчас», фоновая резервная копия и полный экспорт больше не падают с `IDBCursorDirection`.
- Проверены все вызовы `openCursor()` в runtime-коде: используются только допустимые направления (`prev`, `next`) либо направление по умолчанию.

### Причина
Chrome IndexedDB принимает для `IDBCursorDirection` только `next`, `nextunique`, `prev`, `prevunique`. Строка `asc` не является допустимым значением и приводила к синхронному `TypeError` до начала чтения журнала.

## 0.9.0 — фиксированная структура Яндекс Диска, настраиваемый background backup и контекстное меню

### Изменено
- отдельная папка журналов больше не выбирается;
- введена структура `<root>/Upload` и `<root>/Backup/Journal`;
- при проверке служебной структуры проверяется тип существующего ресурса: зарезервированные имена должны быть каталогами;
- PDF сайтов сохраняются только под `Upload`;
- один полный файл backup журнала хранится в `Backup/Journal`;
- служебные папки автоматически проверяются/создаются; ошибка создания входит в общую ошибку операции;
- интервалы фонового backup и retry после ошибки задаются в минутах; default 1440/60;
- просроченный backup выполняется при следующем запуске/возобновлении service worker;
- popup показывает отдельно последнюю успешную и неудачную фоновую попытку;
- добавлено контекстное меню WebClipper, использующее те же page handlers.

### Причина
Пользователь зафиксировал единую управляемую структуру Яндекс Диска, отказался от отдельного выбора папки журнала и потребовал наблюдаемость фоновой выгрузки, управляемые retry-интервалы и доступ ко всему основному workflow через контекстное меню.


## 0.9.3 — индикатор URL, доменный фильтр, месячный импорт, public_url и page upload progress

### Добавлено

- badge = число уникальных локальных дней с успешными копиями URL;
- отдельная верхнеуровневая context-menu команда `Начать выделение WebClipper`;
- иерархический фильтр общего журнала `Все → base domain → third-level domain`;
- месячная навигация выбора backup-файла при импорте с Яндекс Диска;
- сохранение `publicUrl` в journal entry и journal export/import;
- публикация загруженного PDF через Yandex Disk API и отображение постоянной ссылки;
- настройка создания публичных ссылок, default=enabled;
- progress UI обычной отправки страницы на Яндекс Диск;
- `beforeunload` и блокировка конкурирующих WebClip-команд во время page upload;
- служебный UI скрывается только непосредственно на время `Page.printToPDF`, затем возвращается.

### Причина
Пользователю нужна быстрая визуальная оценка свежести копии текущей страницы, удобный поиск по доменам, управляемое восстановление backup по месяцам, устойчивый способ открыть PDF после переименования/перемещения на Диске и прозрачность длительной операции формирования/отправки PDF.

## 0.9.5 — устойчивое live-обновление журнала после reload/update

- Исправлен сценарий, когда уже открытая вкладка журнала после обновления распакованного расширения оставалась в старом extension-context и показывала устаревшее состояние до открытия новой вкладки.
- При смене версии service worker автоматически перезагружает открытые страницы самого расширения.
- Изменение журнала дублируется через `chrome.storage.local.webclipJournalRevision`, поэтому открытые страницы получают независимый сигнал даже если runtime-message был пропущен.
- Журнал перечитывается при `focus`, `pageshow` и возврате вкладки в visible-состояние.
- Добавлен health-check service worker; при инвалидированном extension-context пользователь видит явное требование перезагрузить вкладку.


## 0.9.6 — прямое чтение журнала из IndexedDB

- Исправлен случай, когда `Весь журнал` мог показывать 0 записей при открытии из уже существующей вкладки, хотя новая вкладка видела записи.
- Страница `journal.html` больше не получает список записей через `WEBCLIP_JOURNAL_LIST`; для отображения она напрямую читает `WebClipJournal/entries` из IndexedDB расширения.
- Service worker остаётся владельцем операций записи, удаления, импорта/экспорта и Яндекс Диска.
- Фильтры URL/сайта/доменов применяются к данным, прочитанным непосредственно из IndexedDB.
- Добавлена страховочная синхронизация видимого журнала каждые 3 секунды в дополнение к revision/focus/visibility событиям.

## 0.9.8 — управляемое удаление Yandex-файла из журнала

### Добавлено
- modal выбора действия при удалении Yandex journal entry;
- варианты `keep` и `trash`, причём выбор обязателен;
- папка `<root>/Trash/MM-YYYY` по дате удаления;
- move-before-delete: удалённый файл перемещается и проверяется раньше локального удаления entry;
- `resourceId` для новых Yandex entries и export/import;
- fallback-поиск файла после ручного rename/move по `resourceId` или `publicUrl`;
- защита `beforeunload` на время удаления с сетевой операцией.

### Причина
Пользователь должен явно контролировать жизненный цикл сохранённого PDF. Удаление записи журнала не должно автоматически уничтожать файл, но при выбранном удалении файл должен оставаться восстановимым в управляемой папке приложения. Порядок remote-first предотвращает потерю связи с файлом при ошибке API.
