# WebClip — session execution and interruption-safety policy

Этот документ задаёт постоянные правила выполнения проектной работы в инструментальных сессиях. Он применяется к глубокому аудиту, реализации, исправлениям, тестированию, документации, release/recovery и другим содержательным задачам WebClip.

`PROJECT_MISSION_AND_DEFENSIVE_SECURITY_POLICY.md` остаётся верхнеуровневой продуктовой/security-нормой. `AUDIT_CHANGE_WORKFLOW.md` остаётся обязательным workflow для audit findings и P-owner. Настоящий документ задаёт, **как организовывать каждую инструментальную сессию и как сохранять прогресс при неожиданном прерывании**.

## 1. Обязательное начало каждой содержательной сессии

Перед новой работой необходимо:

1. fresh-fetch текущего `main` и зафиксировать exact SHA;
2. проверить наличие незавершённой работы предыдущей сессии: рабочие ветки, durable commits/evidence, открытые PR, CI, TOCTOU/merge tail;
3. отличить содержательно незавершённый блок от пустой/stale ветки, на которой нет новых durable результатов;
4. сообщить пользователю:
   - есть ли незавершённая работа;
   - точную устойчивую точку продолжения: branch, head SHA, завершённые этапы/блоки и что осталось;
   - краткий план текущей сессии;
   - оценку способности закончить взятые блоки в пределах текущего инструментального окна;
   - конкретные риски переноса на следующую сессию, например движение `main`, внешний CI, mergeability, недоступность внешнего boundary или неожиданно широкий root cause.

Нельзя начинать новый независимый tranche, не разобрав сначала реальное durable состояние предыдущего незавершённого tranche.

## 2. Расчёт объёма работы на инструментальное окно

Работу следует планировать так, чтобы максимально полезно занять всё доступное инструментальное окно и при этом по возможности завершить взятые блоки до конца сессии.

Правила:

- сначала взять реалистичный первый блок, который можно довести до устойчивого результата;
- после первых фактических результатов переоценить темп и расширить объём, если окно позволяет;
- не ограничивать сессию искусственно малым объёмом, если можно безопасно закончить дополнительные независимые блоки;
- не брать заведомо слишком большой монолитный блок, который нельзя сохранить по частям;
- при выборе между количеством и завершённостью предпочитать несколько полностью доказанных и durably сохранённых этапов одному большому незавершённому исследованию;
- если основной tranche полностью завершён и остаётся существенная часть окна, допускается начать следующий независимый tranche только при условии, что до конца сессии будет создан хотя бы один однозначный durable checkpoint либо будет явно сохранена безопасная нулевая точка без ложного заявления о завершённых результатах.

## 3. Работа только этапами с durable checkpoints

Любая длинная работа должна быть разбита на значимые этапы. После каждого этапа substantive progress должен переходить из ephemeral состояния в устойчивое состояние репозитория.

Durable checkpoint может включать:

- commit с audit/evidence документом;
- commit с runtime + deterministic tests + соответствующим evidence;
- безопасный integration commit после движения `main`;
- открытый PR с exact reviewed head;
- завершённый exact-head CI;
- post-merge confirmed `main` + CI.

Для глубокого аудита естественный размер checkpoint — группа логически связанных блоков; обычно следует сохранять evidence после каждых примерно 8–16 существенных блоков или раньше, если уже получен важный самостоятельный вывод. Это ориентир, а не причина искусственно дробить маленькую задачу.

Нельзя оставлять единственный экземпляр важного результата только:

- в локальном временном файле;
- в памяти инструмента/браузера;
- в тексте чата;
- в незакоммиченном рабочем состоянии.

## 4. Содержимое checkpoint, достаточное для гарантированного продолжения

Устойчивое состояние должно позволять следующей сессии продолжить работу без реконструкции скрытого контекста.

Для незавершённого tranche checkpoint должен по возможности фиксировать:

- exact audited baseline `main` SHA;
- branch и exact durable head SHA;
- что уже завершено и доказано;
- какие блоки/проверки остались;
- rejected/negative controls, чтобы их не повторять как новые findings;
- duplicate/root-cause classification и текущих owner, если они уже определены;
- важные reproduction parameters и physical/CI evidence;
- known external risks/unknowns;
- ожидаемый следующий шаг.

Если ветка существует, но новых commits/evidence на ней нет, следующая сессия должна прямо сказать, что содержательного durable прогресса на ней нет, а не представлять её как завершённый checkpoint.

## 5. Защита от неожиданного прерывания

Рабочий порядок должен предполагать, что инструментальная среда может завершиться после любого значимого действия.

Поэтому:

1. не накапливать длинную цепочку уникальных результатов без commit/evidence;
2. сначала закреплять уже доказанное, затем переходить к следующей группе экспериментов;
3. перед рискованным integration/rebase/merge действием иметь отдельный recoverable head;
4. после конкурентного движения `main` не выполнять blind merge — сначала сравнить changed files/root-cause overlap и создать безопасный integration checkpoint;
5. после каждого существенного изменения ветки повторно знать её exact SHA;
6. не считать работу доставленной до подтверждения canonical `main` и обязательного post-merge CI, если этот workflow применим.

## 6. Обязательные промежуточные сообщения пользователю

Во время длинной сессии следует коротко сообщать о прогрессе после значимых стадий, а не только в финале.

Полезное промежуточное сообщение сообщает одно или несколько из следующего:

- новый подтверждённый finding/negative control;
- durable checkpoint SHA;
- изменение оценки объёма или root cause;
- движение `main`/конкурентный PR и принятое безопасное решение;
- переход к delivery/CI/TOCTOU;
- точную оставшуюся работу.

Не следует перегружать пользователя низкоуровневым перечислением каждого tool call.

## 7. Правило продолжения следующей сессии

Следующая сессия обязана начинать не с предположений, а с проверки durable state:

`fresh main -> branches/PR/CI/checkpoints -> exact resume point -> user start report -> continuation`.

Если ранее заявленный незавершённый tranche уже был завершён другой конкурентной веткой/PR, сначала подтвердить это по `main`, diff и CI, затем не дублировать работу и выбрать новый независимый root-cause tranche.

Если `main` изменился после checkpoint, старый baseline не объявляется current truth. Нужно выполнить fresh duplicate/overlap/TOCTOU check и только затем продолжать/интегрировать.

## 8. Delivery tail является частью взятого блока

Если цель сессии включает доставку изменений, завершённость означает не только написанный код/evidence.

Нормальный tail:

`fresh main -> exact compare -> PR -> exact-head Repository integrity SUCCESS -> fresh TOCTOU (main/base/head/mergeability/files) -> expected-head merge -> confirm new main -> post-merge Repository integrity SUCCESS`.

Если сессия прерывается внутри этого tail, следующий стартовый отчёт должен точно указать последнюю завершённую ступень: например, PR открыт, exact-head CI success, но fresh TOCTOU/merge ещё не выполнены.

## 9. Правдивость статуса

Нельзя:

- называть tranche завершённым до завершения реально взятого acceptance/delivery tail;
- обещать фоновое или асинхронное продолжение вне текущей сессии;
- скрывать, что часть работы существует только как exploratory result без durable evidence;
- выдавать stale branch за current baseline;
- повторять уже завершённый concurrent tranche как новую работу.

Частично выполненная работа допустима, если она честно классифицирована и сохранена так, что следующая сессия гарантированно продолжит её с точной точки.

## 10. Постоянный характер правила

Эти требования являются постоянным project workflow и применяются по умолчанию ко всем последующим содержательным инструментальным сессиям WebClip.

Изменить или отменить их можно только явным последующим решением пользователя, зафиксированным в durable project policy. Обычная экономия времени, новый чат, смена tranche или смена исполнителя не отменяют эти правила.
