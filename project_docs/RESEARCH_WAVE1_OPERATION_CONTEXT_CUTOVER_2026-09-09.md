## 1. Purpose

The preceding Wave 1 research now defines both sides of the save pipeline:

```text
trusted reviewed source
-> worker save admission
-> exact render generation
-> immutable PDF generation {G,N,H}
```

and:

```text
immutable PDF generation
-> immutable destination context
-> exact external content proof
-> publication policy
-> Journal CAS finalization
```

A compatibility problem remains between those architecture blocks.

Current WebClip uses the single textual field `operationId` for several semantically different jobs:

```text
UI progress correlation
OperationLog durable primary key
pending local-download identity
pending remote-save provenance
prepared Save As provenance
backup lease/progress correlation
Journal historical provenance / local OperationLog link
caller-visible support/debug id
```

The field is sometimes caller-generated and sometimes worker-generated. Therefore a mechanical rename `operationId -> physicalOperationId` would be incorrect. This tranche defines the exact staged cutover.

## 2. Current source proof

### 2.1 Caller text currently becomes physical execution identity

The save dispatcher passes `normalizeOperationIdInput(message.operationId)` directly into `generatePdfAndDownload()`, `generatePdfAndUploadToYandex()` and cached retry helpers.

Those helpers use the pattern:

```js
operationId = String(operationId || '') || makeOperationLogId(...);
```

Therefore today's rule is conditional:

```text
caller supplies operationId -> caller chooses physical identity
caller omits operationId   -> worker chooses physical identity
```

This is the P1-198 conflation.

### 2.2 OperationLog physically keys by the same string

`WebClipOperationLogs` currently uses:

```text
operations keyPath = operationId
events keyPath     = [operationId, seq]
```

`startOperationLog(operationId, ...)` and `recordOperationStage(operationId, ...)` therefore consume the same text as a physical diagnostic namespace.

### 2.3 Content/options/journal use it as legitimate presentation correlation

Current content state keeps `pageUploadOperationId`, generates a UUID before a save/retry, and accepts progress only if `message.operationId === state.pageUploadOperationId`.

Options and Journal surfaces similarly keep values such as:

```text
activeBackupOperationId
activeDeleteOperationId
activeMoveReadOperationId
```

This is a valid presentation/correlation role, but it is not physical ownership.

### 2.4 Pending local download elevates correlation into physical namespace

Current `makePendingLocalDownloadIntentKey(operationId)` prefers caller text when constructing `intent:<suffix>`. Current reconciliation also contains an equality path where `existing.operationId === intent.operationId` contributes to physical sameness.

That must not survive P1-198.

### 2.5 Pending remote save and Journal persist the same field

Remote checkpoints persist `operationId`; locally created Journal entries also persist `operationId`. Portable import can bring an `operationId` back into a local Journal row.

P1-190 already proves imported portable text cannot be a live local OperationLog foreign key.

### 2.6 Positive controls already exist

Several subsystems already have the stronger architecture pattern:

```text
prepared Save As -> saveAsSessionId
staged import    -> stagingId / preview receipt / leaseToken / ownerSessionId
backup lease     -> opaque lease token
```

These demonstrate that domain continuation authority can and should remain separate from generic correlation.

## 3. Core conclusion: old `operationId` must split into three concepts

The target needs three client/worker identities, not merely two.

### 3.1 `clientRequestId`

Purpose:

```text
exact admission lookup / lost-response reconciliation / request deduplication
```

Properties:

- generated by updated WebClip UI for one intended request;
- bounded opaque text;
- expected fresh for each new intended request;
- caller-controlled, therefore not an ownership capability;
- same id + same immutable fingerprint returns the existing worker receipt;
- same id + different fingerprint fails closed;
- never becomes an OperationLog physical key merely because normal UI generates random UUIDs.

This is the P1-210 admission correlation.

### 3.2 `clientCorrelationId`

Purpose:

```text
optional display/grouping/support correlation
```

Properties:

- may repeat;
- may be absent;
- useful for progress UI, search and support;
- no dedup semantics;
- no continuation semantics;
- no physical-operation semantics.

This preserves P1-198's requirement that distinct physical actions may share generic correlation metadata.

### 3.3 `physicalOperationId`

Purpose:

```text
identity of one physical worker execution instance
```

Properties:

- always worker-issued for new v2 operations;
- opaque and collision-resistant;
- unique per physical admission;
- OperationLog physical key for new v2 rows;
- durable where recovery/reconciliation requires it;
- stored as provenance in domain checkpoints;
- not a universal authorization token;
- continuation still requires the domain receipt/lease/CAS.

## 4. Why request and correlation must remain different

P1-198 and P1-210 would conflict if both were represented as one `clientOperationId`.

P1-198 needs a repeatable client correlation that cannot collapse independent operations.

P1-210 needs a request correlation whose exact replay is deduplicated to the already admitted physical operation after an outer response is lost.

Therefore:

```text
clientRequestId
    unique per intended request; durable lookup/dedup

clientCorrelationId
    optional repeatable display/grouping value
```

During migration the current UI may generate one UUID and temporarily place it in both fields, but the worker must keep the semantics separate.

## 5. Legacy `message.operationId` mapping

A legacy field cannot silently become a stronger v2 capability.

Required rule:

```text
incoming legacy message.operationId
-> clientCorrelationId only
```

It does not become `physicalOperationId` and does not automatically become `clientRequestId`.

Updated v2 surfaces should explicitly send:

```js
{
  clientRequestId,
  clientCorrelationId,
  operationId: clientCorrelationId // temporary compatibility only
}
```

An unmigrated caller sending only `operationId` receives a fresh worker physical operation each time. That preserves safe legacy behavior without caller-keyed deduplication.

## 6. Target `OperationContextV2`

Conceptual worker-only immutable context:

```js
{
  schemaVersion: 2,

  physicalOperationId,
  clientRequestId,
  clientCorrelationId,

  operationKind,
  subjectKey,
  requestFingerprint,
  admittedAt,

  sourceGenerationId,
  sourceReceiptRef,

  senderContext: {
    tabId,
    browserDocumentId,
    frameId,
    documentLifecycle
  }
}
```

Rules:

1. ordinary execution code does not mutate this context;
2. caller input never fills `physicalOperationId`;
3. `sourceGenerationId` remains separate from physical operation identity;
4. destination/resource identity remains separate;
5. the context is an identity/provenance primitive, not a giant universal capability.

## 7. A durable admission receipt is required

P1-210 requires recovery when the outer `runtime.sendMessage()` result is lost.

OperationLog cannot be the durable admission authority because:

- it is diagnostic;
- users can clear it;
- retention is configurable;
- quota cleanup may remove diagnostics;
- its `success/error` state cannot prove external effect settlement;
- P1-197/P1-205 govern its own history lifecycle.

### Recommended store

Create a dedicated worker-owned IndexedDB:

```text
DB      = WebClipOperationReceipts
version = 1
store   = receipts
keyPath = physicalOperationId
```

Recommended indexes:

```text
clientRequestId   unique and sparse by omission
kindSubjectKey    non-unique
updatedAt         non-unique
phase             non-unique
```

Background operations omit `clientRequestId` instead of storing an empty string so the unique index does not collide on empty values.

### Why not place receipts in `WebClipOperationLogs`

The following must be mechanically true:

```text
OperationLog clear       != operation receipt clear
OperationLog retention   != functional recovery retention
OperationLog quota purge != effect authority purge
```

### Why not place them in `WebClipJournal`

`journal.js` directly opens the shared Journal DB. A common receipt store there would turn every receipt schema change into a worker/journal-page IndexedDB version-coordination problem. A dedicated worker-only DB has a smaller authority surface.

## 8. Admission receipt schema

Conceptual durable record:

```js
{
  schemaVersion: 1,

  physicalOperationId,
  clientRequestId,
  clientCorrelationId,

  operationKind,
  subjectKey,
  requestFingerprint,

  admittedAt,
  updatedAt,
  phase,
  effectBoundary,

  sourceGenerationId,

  domainReceipt: {
    kind,
    id
  } | null,

  terminalAt
}
```

The record must remain small and non-secret. It must not persist OAuth tokens, Authorization headers, signed Yandex URLs, PDF bytes, full Journal payloads, comments, or arbitrary host-page HTML.

## 9. `subjectKey`

`subjectKey` supports bounded read-only discovery when the page loses local variables.

Examples:

```text
journal-entry:<entryId>
backup:<journalGeneration>
save:<sourceGenerationId>:yandex
save:<sourceGenerationId>:download
prepared-save-as:<saveAsSessionId>
import-staging:<stagingId>
```

It must be a bounded normalized internal identity, not an arbitrary full URL.

Discovery must never choose one of several candidates simply because it is newest:

```text
0 candidates -> none / not-admitted
1 exact candidate -> present read-only
>1 candidates -> ambiguous, fail closed
```

A reloaded source page must not use a broad same-tab query to inherit an older document's operation.

## 10. `requestFingerprint`

A caller-controlled request id cannot be rebound to another request.

The worker should store:

```text
SHA-256(versioned canonical immutable admission arguments)
```

The canonical representation should include operation kind, subject key, exact source receipt identity where applicable, destination class, immutable options and exact subject revision/generation.

It must exclude secrets, signed URLs and volatile progress data. The fingerprint is comparison evidence, not a capability.

## 11. Atomic admission algorithm

```text
validate sender + schema
        ↓
normalize immutable arguments
        ↓
construct subjectKey + requestFingerprint
        ↓
BEGIN receipt transaction
        ↓
lookup clientRequestId if present
        ├─ same kind/subject/fingerprint
        │      -> return existing physical receipt
        │         zero second physical admission
        │
        ├─ mismatch
        │      -> CLIENT_REQUEST_CORRELATION_MISMATCH
        │
        └─ absent
               -> issue physicalOperationId
               -> add phase=admitted receipt
COMMIT
        ↓
start diagnostic OperationLog under physicalOperationId
        ↓
only then start work
```

The functional receipt commit must precede any work whose outer result may be lost.

## 12. Capacity and cleanup

The receipt store must be bounded.

If active capacity is exhausted:

```text
reject the new operation before effect admission
```

Do not evict another active operation.

Terminal cleanup may remove old common admission state only when:

1. the receipt is terminal;
2. terminal retention elapsed;
3. no referenced domain checkpoint/effect receipt still needs it;
4. deleting the common receipt does not change the domain/external fact.

## 13. OperationLog compatibility without changing its keyPath

The current OperationLog store can keep `keyPath = operationId`.

For new rows:

```js
{
  identityVersion: 2,
  operationId: physicalOperationId, // compatibility storage/API alias
  physicalOperationId,
  clientRequestId,
  clientCorrelationId,
  ...diagnostic fields
}
```

Thus `OperationLog.operationId` becomes a documented physical id for v2 rows.

Legacy rows without v2 metadata are classified:

```text
legacy-conflated
```

Their old value is retained as historical diagnostics and is never promoted to trusted worker-issued identity by syntax or migration.

No OperationLog DB version bump is required solely to add these fields. Durable request lookup belongs in `WebClipOperationReceipts`, not an OperationLog index.

## 14. OperationLog helpers should consume context

Prefer APIs such as:

```text
startOperationLog(operationContext, ...)
recordOperationStage(operationContext, ...)
finishOperationLog(operationContext, ...)
```

or physical-only internal helpers whose names make the requirement explicit.

Do not keep a normal new-operation path where any arbitrary string passed as `operationId` selects the durable log namespace.

## 15. Progress compatibility

Current progress payloads expose one `operationId`, and old UI filters against it. Changing that field immediately to physical id would break current content/options/journal behavior.

### Transitional v2 payload

```js
{
  identityVersion: 2,

  // deprecated presentation compatibility alias only
  operationId: clientCorrelationId || clientRequestId || physicalOperationId,

  clientRequestId,
  clientCorrelationId,
  physicalOperationId,

  stage,
  message,
  percent,
  state
}
```

Critical internal rule:

```text
recordOperationStage(physicalOperationId, ...)
```

must be separate from the presentation alias.

## 16. Page/UI state during cutover

Current variables such as `pageUploadOperationId`, `activeBackupOperationId`, `activeDeleteOperationId` and `activeMoveReadOperationId` should split conceptually into:

```text
activeClientRequestId
activeClientCorrelationId
activePhysicalOperationId
```

At user action start:

```text
generate clientRequestId
choose/generate clientCorrelationId
activePhysicalOperationId = empty
```

On the first valid v2 receipt/progress for the exact request:

```text
capture physicalOperationId
```

After that, later progress requires both request and physical identity to match.

This is presentation fencing only; it does not authorize retry/cancel/domain mutation.

## 17. P1-210 lost-response composition

A normal v2 result can return:

```js
{
  ok,
  identityVersion: 2,
  clientRequestId,
  clientCorrelationId,
  physicalOperationId,
  operationState,
  domainResult
}
```

If the outer result is lost, the UI state is:

```text
unknown
```

not `failed`.

The UI uses a read-only protocol equivalent to:

```text
WEBCLIP_USER_OPERATION_RECONCILE
```

by `clientRequestId` when available, or bounded kind+subject discovery after local page state was lost.

Repeating the exact same `clientRequestId` and exact fingerprint returns the already admitted worker receipt and does not start a second physical effect.

## 18. Why repeatable correlation remains safe

Example:

```text
clientCorrelationId = project-X
request RA -> physical PA
request RB -> physical PB
```

Required:

```text
PA != PB
```

The unique/dedup key is `clientRequestId`, never `clientCorrelationId`.

## 19. Legacy callers

For an old caller sending only:

```text
operationId = L
```

worker interpretation is:

```text
clientCorrelationId = L
clientRequestId = absent
physicalOperationId = fresh worker id
```

Sending L twice therefore still creates two distinct physical operations. Legacy callers do not gain request-dedup authority merely because P1-210 exists.

All user-facing non-idempotent surfaces covered by P1-210 must eventually be migrated to explicit `clientRequestId` before P1-210 can close.

## 20. Local-download migration

V2 pending local-download state should contain:

```text
downloadIntentId          worker/domain-issued
physicalOperationId
clientRequestId
clientCorrelationId
sourceGenerationId
pdfGeneration
expectedBytes
...existing exact download effect evidence
```

Physical matching uses `downloadIntentId`, exact DownloadItem/effect evidence and physical provenance where appropriate.

It does not use client correlation equality as physical sameness.

A legacy row containing only old `operationId` is classified:

```text
legacy-conflated-no-physical-authority
```

Existing stronger DownloadItem/domain evidence remains usable under its owner; no physical id is synthesized from legacy text.

## 21. Remote-save migration

Wave 1 remote checkpoint V2 should contain:

```text
physicalOperationId
clientRequestId
clientCorrelationId
sourceGenerationId
pdfGeneration
byteLength
sha256
account/root/context generation
publication policy generation
expected Journal generation
remote settlement receipt
```

The common operation receipt stores only a small reference:

```js
domainReceipt: { kind: 'remote-save', id: remoteSaveId }
```

Remote effect truth remains in the remote checkpoint.

Legacy remote `operationId` remains diagnostic/historical only and cannot be promoted to physical ownership.

## 22. PDF/cache relationship

The identity chain is explicitly:

```text
physicalOperationId = physical execution
sourceGenerationId   = admitted source
G                    = immutable PDF object generation
N                    = exact bytes
H                    = SHA-256 of exact bytes
```

None substitutes for another.

P0-079 V4 must consume real physical/source provenance before its exact retry semantics can be considered trusted.

## 23. Prepared Save As

`saveAsSessionId` remains continuation authority.

The checkpoint may add:

```text
physicalOperationId
clientRequestId
clientCorrelationId
sourceGenerationId/pdfGeneration
```

but:

```text
same physicalOperationId + wrong saveAsSessionId -> cannot continue
correct current saveAsSessionId -> may continue under P1-156
```

Physical identity is provenance, not a replacement for the purpose-specific session handle.

## 24. Backup lease

Current backup lease already has an opaque token. Target semantics:

```text
leaseToken          = lease/ownership authority
physicalOperationId = execution provenance
clientRequestId     = manual-request recovery correlation when applicable
clientCorrelationId = optional display correlation
```

Periodic background backup has no `clientRequestId` and still gets a worker-issued physical id.

## 25. Journal local provenance and P1-190

A new local Journal row should have a worker-minted entry-bound local OperationLog link, conceptually:

```js
{
  operationId: clientCorrelationId || clientRequestId || '', // portable compatibility only
  clientRequestId,
  sourceGenerationId,
  operationLink: {
    version: 2,
    provenance: 'live-local',
    entryId,
    physicalOperationId
  }
}
```

Automatic local OperationLog linking is authorized by `operationLink`, not by regex-valid `entry.operationId`.

Portable import must demote operation text to `historicalOperationId` / `imported-unverified` and strip any portable `operationLink`. Importing back into the same profile does not restore live-local authority.

## 26. Generic bare-id OperationLog finishing must disappear

Current Journal import cancellation can send:

```text
WEBCLIP_OPERATION_LOG_FINISH { operationId }
```

That is incompatible with worker-issued identity.

Target cancellation/finalization is domain-driven:

```text
validate stagingId / leaseToken / current domain receipt
        ↓
worker resolves the owning physicalOperationId internally
        ↓
worker finishes that physical OperationLog
```

The generic finish message should be removed, restricted to trusted internal use, or require a domain continuation receipt. Knowledge of textual id alone must not select another operation's lifecycle.

## 27. OperationLog browsing remains diagnostic

General list/get/export may continue. For v2 logs:

```text
operationId == physicalOperationId
```

Options search should eventually include:

```text
physicalOperationId
clientRequestId
clientCorrelationId
title
description
type
status
summary
```

Journal automatic linkage remains governed by the P1-190 local `operationLink` receipt.

## 28. MV3 restart state machine

### R1 — receipt committed, effect not started

```text
phase=admitted
no sealed PDF
no domain effect receipt
worker stops
```

Recovery can determine that no non-cancellable downstream effect was admitted and may transition to `failed-before-effect` before a new request is enabled.

### R2 — rendering, no sealed PDF

If restart leaves no authoritative `{G,N,H}` and no downstream effect checkpoint, the old live source cannot simply be rerendered. A new render requires a fresh source admission.

### R3 — sealed PDF exists

The receipt references exact P0-079 G. Later tab navigation does not change G. Recovery works from exact sealed bytes.

### R4 — local download intent exists

The common receipt references `downloadIntentId`. Local-download owner becomes authoritative.

### R5 — remote save intent exists

The common receipt references `remoteSaveId`. Remote effect owner becomes authoritative.

### R6 — outer response lost

UI reconciles common + domain receipts read-only. Caller/page disappearance is not cancellation.

## 29. Effect-boundary ordering

Before each non-cancellable/external effect:

```text
create exact domain checkpoint
        ↓
link common receipt to it
        ↓
only then invoke effect
```

Examples:

```text
before chrome.downloads.download -> durable local download intent
before Yandex upload start       -> durable remote save intent
before publish                    -> durable publication admission phase
```

This avoids inferring effect truth from progress or OperationLog text after restart.

## 30. Legacy-state classification

| Legacy state | Required classification |
|---|---|
| OperationLog row with plain `operationId` | `legacy-conflated` diagnostics |
| Local Journal row with plain `operationId` | `legacy-unverified` under P1-190 |
| Imported Journal operation text | `imported-unverified` |
| Pending local download with old `operationId` | domain evidence may survive; old id is not physical authority |
| Pending remote save with old `operationId` | remote/domain evidence may survive; old id is not physical authority |
| Prepared Save As | `saveAsSessionId` remains domain authority |
| Backup lease/checkpoint | lease token/generation remains authority |
| Ephemeral progress state | no durable migration; reconstruct from receipts |

Forbidden migrations include both:

```text
legacy operationId X -> physicalOperationId X
```

and:

```text
legacy row -> generate random physical id now -> claim historical physical provenance
```

Both fabricate authority.

## 31. Wire protocol during staged cutover

Preferred new mutation request:

```js
{
  type: '...',
  clientRequestId,
  clientCorrelationId,
  ...domain payload
}
```

Temporary old compatibility may also send:

```text
operationId = clientCorrelationId
```

New result/progress returns all v2 identities.

Read-only reconciliation uses `clientRequestId` or bounded domain subject discovery and never starts a mutation.

## 34. Content-page progress after source loss

P0-070 adds a source-document rule:

```text
progress to source page -> exact documentId target where feasible
```

A new document in the same tab must not become presentation target for an old operation merely because tabId is reused.

If the old source document disappears, durable work may continue; lost progress painting is not cancellation. A new page reconciles read-only and does not inherit old save authority.

## 35. Request dedup is not authorization

The worker may resolve:

```text
clientRequestId R + fingerprint F -> physical P
```

This only means R is a lookup key into worker-owned state.

It does not mean a caller who knows R or P may arbitrarily cancel, finish, retry or mutate that operation. Continuation remains controlled by exact domain receipts.

## 36. Privacy/trust boundary

Trust hierarchy:

```text
caller ids                    = untrusted correlation/lookup inputs
worker physical id            = worker-issued identity primitive
common admission receipt      = worker-owned durable admission mapping
domain receipt / lease / CAS  = continuation/effect authority
external verification         = effect settlement truth
```

The common receipt should retain opaque ids, generation ids, bounded subject keys, a SHA-256 request fingerprint and small status fields. It should not persist secrets, signed transport URLs, PDF bytes, comments or raw host payload.

## 37. Failure semantics

### Admission storage failure

```text
no durable receipt -> no operation effect starts
```

### OperationLog failure

Diagnostic failure does not rewrite functional truth or fabricate effect failure.

### Progress delivery failure

Presentation-only; durable operation state remains authoritative.

### Reconcile response lost

Remain `unknown`; do not unlock mutation retry merely because the read-only query also failed.

### Client request correlation mismatch

Fail closed before effect; never rebind the request id.

## 38. Recommended rollout sequence

### Stage A — pure identity helpers + receipt DB

Add `OperationContextV2`, `WebClipOperationReceipts`, admission/reconcile and legacy classifiers. No existing effect switched yet.

### Stage B — progress/result compatibility

Add v2 fields while retaining temporary old presentation alias. Update UI helpers to track request + physical ids.

### Stage C — Wave 1 save paths first

Migrate:

```text

WEBCLIP_RETRY_PDF_TO_YANDEX

```

### Stage D — local/remote checkpoint identities

Switch new pending rows to explicit physical/request/source/PDF fields. Preserve old rows as legacy.

### Stage E — OperationLog v2

New logs use physical ids and preserve client metadata separately. Update Options display/search.

### Stage F — Journal provenance

Compose with P1-190 worker-minted local link and import demotion.

### Stage G — backup/import/Save As flows

Move each to operation context + its existing domain continuation handles. Remove bare-id log finishing.

### Stage H — P1-210 reconciliation UI

Enable truthful `unknown -> read-only reconcile -> terminal/not-admitted` behavior on covered user operations.

### Stage I — closure sweep

Only after owner-specific source/deterministic/Chrome/external evidence should Registry statuses change.

## 39. Why not one giant repository-wide rename

`operationId` currently means different things in different code paths. A textual rename across the large service worker would mix display correlation, physical identity, historical Journal provenance, domain continuation handles and portable import state.

The cutover must therefore be semantic and staged.

## 48. Research conclusion

The correct cutover is not `rename operationId`.

It is:

```text
clientRequestId
    = exact user-request admission lookup/dedup correlation

clientCorrelationId
    = optional repeatable presentation/support correlation

physicalOperationId
    = worker-issued physical execution identity

sourceGenerationId
    = exact admitted page/source identity

G/N/H
    = exact immutable PDF byte generation

domain receipt/lease/CAS
    = continuation/effect authority
```

The old `operationId` field may survive temporarily only as a compatibility/presentation container whose semantics are explicitly versioned.

The key migration invariant is:

> **No legacy/caller textual identifier may become stronger merely because a new field name or receipt schema was added around it.**

Wave 1 can now move into staged implementation without requiring compatibility semantics to be invented during production edits.
