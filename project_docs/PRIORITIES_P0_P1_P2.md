# Приоритеты P0 / P1 / P2 — WebClip 0.9.9 WIP

Статусы: `DONE` — реализовано и закрыто подтверждённой проверкой; `REGRESSION` — исправление реализовано и прошло локальные проверки, но обязательно остаётся в реальном regression QA; `PARTIAL` — исправлена только часть задачи; `OPEN` — требует реализации/проверки; `AUDIT` — найдено аудитом и классифицировано, исправление ещё не подтверждено повторным проходом.

Коды вида `P0-001`, `P1-001`, `P2-001` являются **стабильными и уникальными**. После назначения код не меняется при смене статуса и не переиспользуется для другой задачи.

Chrome требует `permissions.request()` именно из user gesture и внутри Chromium `PermissionsRequestFunction` fail-closed проверяет `user_gesture()`; transient activation конечна по времени, поэтому медленный discovery способен закончиться корректно, но сам prompt уже получить `User gesture required`/не стартовать. Это отдельный root cause от P1-157: P1-157 закрывает lifetime/unknown settlement **уже начатого** permission prompt, а здесь prompt может не получить admission. Нужен двухфазный gesture-safe UX: discovery/объяснение origins выполняются заранее без запроса; после этого отдельная явная кнопка `Предоставить доступ` первым activation-sensitive действием вызывает `permissions.request()` на уже подготовленном bounded наборе. Candidate set должен иметь короткий TTL и быть связан с исходной tab/document generation; navigation/закрытие/изменение кандидатов инвалидируют его, а после grant перед injection всё равно выполняется fresh document/permission validation по P1-171/P1-004. Не делать скрытый automatic permission request и не обходить browser prompt. Regression/real Chrome: искусственно задержать discovery > activation window — первый discovery click не пытается request; второй непосредственный grant click стабильно открывает prompt; stale candidate после navigation не используется. Реальный optional permission prompt/revoke остаётся release QA. |

## Продолжение глубокого аудита 2026-08-26 — MV3 background-operation lifecycle ownership

| Код | Приоритет | Статус | Пункт |
|---|---|---|---|
| P1-192 | P1 | OPEN | Длинные фоновые операции запускаются из `chrome.alarms.onAlarm` как fire-and-forget Promise (`runDueJournalBackup(...).catch(...)`, `runLoggedOperationLogCleanup(...).catch(...)`), но сам alarm callback возвращается сразу и не владеет lifecycle незавершённой async-работы. Это критично до offscreen transfer: background backup после alarm может выполнять `stageFullJournalExport()` до 5 минут преимущественно через IndexedDB, и только **после** snapshot создаёт/использует offscreen transfer с heartbeat. Periodic backup alarm одноразовый (`when` без `periodInMinutes`): он уже consumed, а следующий periodic/retry alarm ставится позднее; принудительная выгрузка worker в этом окне оставляет только worker-start self-heal при каком-либо следующем внешнем wake-up. Hourly maintenance alarm повторяющийся, но его собственные cleanup/stats-rebuild стадии также могут содержать >30 с pure-IDB work и регулярно прерываться. Нужен явный lifecycle owner длинной background promise: либо перенос heavy IDB/serialization phase в offscreen/другой durable context, либо bounded keepalive wrapper на время фактической операции (Chrome рекомендует периодический extension API call для exceptional long-running service-worker work) с release только после actual settlement; scheduler/checkpoint должны быть crash-safe даже при kill между alarm fire и next-alarm commit. Не использовать keepalive для сокрытия бесконечных hangs: все текущие stage deadlines/abort сохраняются. Regression/real Chrome QA: forced idle termination во время >30 с backup snapshot/maintenance не теряет future schedule, не оставляет вечный lease/checkpoint и либо операция завершается под lifecycle owner, либо автоматически возобновляется из durable state при гарантированном wake source. P1-077 остаётся про правильный alarm boundary вместо heavy runtime-message fire-and-forget, P1-075/P1-076 — про bounded IDB stages/lease; этот пункт отдельно закрывает **lifetime самой alarm-started background operation**. |

## Продолжение глубокого аудита 2026-08-26 — publication policy generation fence

| Код | Приоритет | Статус | Пункт |
|---|---|---|---|
| P0-078 | P0 | OPEN | Глобальная privacy-настройка `createPublicLinks=false` не fenced против уже начатых/восстанавливаемых Yandex save операций, которые ещё **не выполнили** `resources/publish`. Live `uploadCachedRecordToYandex()` читает config один раз в начале и позже ориентируется на старое `config.createPublicLinks`; durable `pendingRemoteSaves` сохраняет этот bool в checkpoint, а `recoverPendingRemoteSaves()` при `current.createPublicLinks` вызывает `ensureYandexPublicUrl()` без повторной проверки текущей настройки. Поэтому пользователь может в Options явно выключить «Создавать постоянную ссылку», но операция из другой вкладки либо background recovery старого checkpoint после этого всё равно создаст новую публичную ссылку. Нужен publication-policy generation/revocation fence: true→false должен немедленно запрещать любой ещё не начавшийся/не подтверждённый `resources/publish` старой generation; непосредственно перед publish live/recovery должны fresh-read current privacy policy и exact generation, а checkpoint должен различать «upload был инициирован при publish=true» и «publish всё ещё разрешён сейчас». Disable не считать отменой уже завершённого upload и не удалять remote file/Journal metadata; если publish уже фактически мог завершиться с unknown outcome, сохранить durable publication reconciliation и не объявлять его отменённым. Уже существующие подтверждённые public links автоматически не отзывать этой настройкой: их lifecycle остаётся P1-164/P0-069. Import user-settings, direct Options toggle и другие config-write paths должны инкрементировать ту же privacy generation. Regression: unresolved checkpoint с `createPublicLinks=true` + последующий global disable не вызывает новый `resources/publish`; enable после disable применяется только к новой/явно re-authorized operation generation; unknown already-started publish reconciles outcome без blind retry. |


## Продолжение глубокого аудита 2026-08-26 — IndexedDB eviction / durability class

| Код | Приоритет | Статус | Пункт |
|---|---|---|---|
| P1-194 | P1 | OPEN | Journal, recovery checkpoints и служебные IndexedDB WebClip живут в web-platform storage extension origin. Chrome прямо допускает eviction такого storage под сильным storage pressure, если origin не получил persistent storage; `unlimitedStorage` также исключает quota/eviction, но текущий manifest его не запрашивает. WebClip умеет показывать `navigator.storage.persisted()` и имеет ручную кнопку `persist()` в Options, однако persistence не является admission/invariant для Journal или irreversible save flows. При этом код возвращает/логирует `recoveryGuaranteed=true`, когда durable checkpoint лишь успешно committed в обычный IndexedDB. Это переоценивает гарантию: при `persisted=false` Browser способен удалить сам Journal/pending store вместе с единственным recovery evidence после уже физически успешного local/Yandex side effect. Нужен явный durability-class contract: выбрать приемлемую стратегию защиты (например, добиться `navigator.storage.persist()` и контролировать результат; рассмотреть `unlimitedStorage` только как осознанное permission/product решение; либо иной durable layer), показывать состояние пользователю и не маркировать recovery как guaranteed, если eviction protection не доказана. Перед необратимым side effect checkpoint admission должен учитывать не только commit/quota, но и требуемый durability class; если продукт допускает best-effort storage, терминология/UX/OperationLog обязаны это честно отражать. External versioned backup остаётся дополнительной защитой и не заменяет локальный Journal source-of-truth. Regression/real Chrome QA: `persisted=false` не выдаёт ложную `recoveryGuaranteed`; выбранный protected mode подтверждается после restart/storage-pressure simulation настолько, насколько позволяет Chrome test environment. P1-043 остаётся про concurrent quota reservation, P2-008 — про расширенный health-report. |
