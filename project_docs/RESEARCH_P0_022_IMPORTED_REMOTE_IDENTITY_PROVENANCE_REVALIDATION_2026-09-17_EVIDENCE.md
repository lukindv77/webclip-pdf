## Semantic duplicate / root-cause reconciliation

No new P-code is created.

P0-022 owns **provenance of destructive remote object identity**: data that looks like a locator or identifier is not automatically authority to mutate a remote object.

Adjacent owners remain separate:

- **P0-013** — import/restore must remain bound to the exact backup object/staging/content receipt selected by the user;
- **P0-073** — pending remote recovery must remain bound to its exact account/root namespace;
- **P0-074** — a long Yandex operation has one immutable account/root/auth/config context;
- **P0-069** — deletion of a published Journal entry requires explicit publication preserve/revoke outcome;
- **P0-076** — local Journal mutation requires entry revision + Journal-generation CAS;
- **P1-090** — exact Yandex object reconciliation remains a related lower-level identity concern.

P0-013 can prove **which backup bytes** were selected/imported. It does not establish that arbitrary `resourceId`, `publicUrl`, or path strings contained in those bytes were originally issued by Yandex for the destructive target now being operated on.

## Fresh current-source proof

### 1. Import normalization accepts remote-identity-looking fields as ordinary data

Current `service-worker.js::normalizeImportedJournalEntry()` copies these imported fields into the normalized Journal entry:

- `remotePath`;
- `folder`;
- `publicUrl`;
- `resourceId`;
- `accountUid`;
- `rootPath`.

`publicUrl` is syntactically normalized and `resourceId` is bounded as a string, but no separate field marks whether the values were:

- generated by a current WebClip save and verified against Yandex;
- observed from the current Yandex API during reconciliation;
- merely carried inside a legacy/imported backup.

Therefore the resulting record loses the distinction between **locator metadata** and **proven destructive identity authority**.

### 2. Import content receipts prove bytes, not remote provenance

Current import pipeline has strong integrity/admission controls:

- staging generation;
- `contentSha256`;
- entry count;
- source (`file` / `yandex`);
- expected Journal revision;
- explicit replace confirmation.

Those controls are valuable positive evidence for P0-013 and import consistency.

But a content digest proves that the staged import bytes did not silently change between preview and commit. It does not prove the external truth of a field embedded in those bytes. An imported JSON object can be byte-exact while containing stale, copied, legacy, or otherwise unproven remote identifiers.

### 3. Destructive locator promotes stored fields to expected identity

Current `findYandexFileForJournalEntry(entry)` derives:

- `expectedResourceId` from `entry.resourceId`;
- `expectedPublicUrl` from `entry.publicUrl`;
- `expectedAccountUid`;
- `expectedRootPath`;
- stored path and filename.

Its matching rule treats a non-empty stored `resourceId` as primary expected identity. If Yandex metadata for a candidate has the same `resource_id`, that candidate is accepted, subject to public-link consistency when both sides expose one. If `resource_id` is absent from a candidate response, an exact public URL may serve as secondary identity.

This is a sound matching rule **only if the expected identity itself has trusted provenance**.

For a current native save, the identifier may come from Yandex metadata after upload/reconciliation. For an imported/legacy record, current source does not retain a provenance class that distinguishes such provider-observed identity from a string supplied by imported data.

### 4. The same locator feeds destructive workflows

Current Journal destructive paths call the remote locator before physical operations such as moving a Yandex file to WebClip Trash. The modern path has useful safeguards:

- account/root checks;
- exact `resource_id` comparison when available;
- refusal to rely on path alone after relocation when stronger identity is missing;
- conflict detection rather than heuristic first-match selection.

These are positive controls, but they do not cure imported provenance. A matcher cannot infer that an `expectedResourceId` is trustworthy merely because its syntax is valid and a current object with that ID exists.

## Failure schedules

### Imported identifier promotion

1. Backup/import record contains `resourceId = R2`.
2. The import is byte-exact and passes `contentSha256`.
3. The record is committed into Journal with no remote-identity provenance class.
4. Later, a destructive workflow opens the record.
5. `findYandexFileForJournalEntry()` treats `R2` as expected identity.
6. A current Yandex object `O2` legitimately has resource ID `R2`.
7. The matcher can regard `O2` as the intended target because stored `R2` is indistinguishable from provider-verified identity.
8. A destructive operation may therefore be authorized by imported metadata rather than by a current proof tying the Journal record to `O2`.

The defect does not require guessing resource IDs or bypassing Yandex authentication. The authority boundary is wrong even when all strings are well formed: **imported data becomes destructive authority without a provenance transition**.

### Imported public capability promotion

1. Legacy/imported record contains a public URL but no verified private resource receipt.
2. Current matching allows exact `public_url` to serve as identity in some response shapes, especially where a candidate omits `resource_id`.
3. The public URL can aid discovery/reconciliation.
4. But public capability equality alone does not establish that the current private-account object is authorized for destructive mutation under the current account/root context.
5. Destructive authority must therefore require a current private-provider observation receipt before mutation.

### Positive control: current provider observation

1. Imported record provides path/public URL/resource ID only as hints.
2. WebClip resolves the candidate in the immutable current account/root context.
3. Yandex returns current private metadata for one exact object, including stable identity fields available to the API.
4. WebClip creates a bounded immutable receipt identifying:
   - account identity/context generation;
   - root namespace;
   - current `resource_id`;
   - current path as observation data;
   - public identity if relevant;
   - observation generation/time and operation identity.
5. The destructive command consumes that receipt and refuses late retargeting.
6. Imported locator values may constrain discovery or expose conflicts, but they do not themselves authorize the mutation.

## User-facing relevance

A portable backup is expected to restore the user's history, not silently grant destructive authority over whichever current Yandex object happens to match an imported identifier. The safest user-visible behavior for an unproven legacy binding is therefore:

- continue to show the historical record;
- allow non-destructive viewing/reconciliation where safe;
- require explicit/current remote reconciliation before destructive mutation;
- fail closed or require manual resolution when exact current object identity cannot be proven.

No reliable independent community report was found that is precise enough to use as defect proof; none is asserted here.

## Required invariant

**Imported/legacy locator fields are hints, not destructive capabilities.**

A destructive Yandex operation must consume an exact remote-object receipt produced from a current provider observation inside the immutable operation context. The receipt cannot be fabricated solely from imported Journal fields.

At minimum:

1. imported `remotePath`, `publicUrl`, `resourceId`, filename, account/root strings are classified as unverified unless they carry a separately proven current-provider provenance;
2. import `contentSha256` / staging generation remain content-integrity receipts only;
3. discovery may use imported fields as bounded hints;
4. destructive admission requires current private-provider reconciliation;
5. the provider observation must bind account/root context plus exact remote identity;
6. conflicting stronger identity fails closed;
7. once admitted, the destructive command consumes the immutable receipt and cannot re-read/rebind to a different imported locator.

## Acceptance shape

1. **Explicit provenance class.** Journal/operation data distinguishes `imported-unverified`, `legacy-unverified`, and `provider-verified` remote identity, or an equivalent representation with the same authority semantics.
2. **No promotion during import.** `normalizeImportedJournalEntry()` cannot turn a portable `resourceId/publicUrl/path` string directly into destructive authority.
3. **Digest separation.** Import SHA/generation proves selected content bytes, not external object truth.
4. **Current provider reconciliation.** Before move/delete/unpublish or another destructive action, resolve the object against current Yandex metadata under P0-074 immutable account/root context.
5. **Exact object receipt.** Persist or hold an immutable operation receipt with current provider-observed remote identity and bounded observation metadata.
6. **Public link is not enough.** A public capability may help discovery but destructive private-account mutation still requires current exact private object proof.
7. **Path is not enough after change.** Existing fail-closed behavior for path-only relocated legacy records is preserved.
8. **Conflict handling.** A verified-native stored identity conflicting with current observation fails closed; an unverified imported identity is treated as a hint/conflict signal, not authority.
9. **No late retarget.** Physical destructive code consumes the receipt generated for that operation and rejects a different target.
10. **Account/root binding.** P0-073/P0-074 namespace/context checks remain mandatory.
11. **Publication composition.** If the object is public, P0-069 still requires explicit preserve/revoke settlement.
12. **Journal CAS.** P0-076 still gates final local mutation after external settlement.
13. **Legacy usability.** Old records remain readable; failure to prove remote identity must not corrupt or silently delete them.

## Production implementation tranche — 2026-09-19

Production changes:

- Journal remote identity now carries one explicit provenance class: `provider-verified`, `imported-unverified`, or `legacy-unverified`;
- import normalization always downgrades portable locator metadata to `imported-unverified`, even if imported bytes claim stronger provenance;

- move outcome must retain the exact receipt `resource_id`;
- existing P0-076 Journal generation/revision CAS remains the final local-mutation gate.
