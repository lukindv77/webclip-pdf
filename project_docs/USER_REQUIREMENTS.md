# Требования и замечания пользователя — WebClip

Этот файл предназначен для передачи контекста в новый чат. Формулировки ниже — нормализованная фиксация требований, а не дословная стенограмма.

## Базовая задача

Создать Chrome Extension с функциональностью WebClipping.

## Выделение областей

1. Пользователь должен иметь возможность выделить одну или несколько областей страницы.
2. Изначально требовались непересекающиеся области; позже модель уточнена:
   - пользователь может выбрать более крупную новую область, которая включает ранее выбранные;
   - такое поведение штатно;
   - новая родительская область «Включены» может заменить дочерние области «Включены».
3. Области могут быть смежными и принадлежать одному родителю.
4. В выбранную область должны входить все её элементы и дочерние элементы.
5. Должна быть возможность исключить из областей «Включены» частично вложенные области, например рекламный блок внутри статьи.
6. Исключённые области должны сохраняться при последующем выборе более крупного родителя области «Включены», если всё ещё находятся внутри него.
7. Нужны два явных режима: добавление и исключение.
8. Кнопка «Основной контент» должна сразу выбрать типовую область с контентом, после чего пользователь может добавлять области «Включены» или создавать области «Исключены».
9. Расширение не должно самостоятельно исключать то, что считает рекламой.
10. Допустима отдельная функция «Найти рекламу», которая только предлагает/подсвечивает кандидатов; окончательное решение принимает пользователь.

## Спойлеры и сворачиваемые блоки

1. Полезный скрытый контент желательно включать в PDF там, где его можно безопасно представить без выполнения произвольной бизнес-логики страницы.
2. WebClip не должен synthetic-click произвольные accordion/toggle/link/submit controls и не получает authority на navigation/submit/application side effects ради печати.
3. Допустимы inert/static print representation и безопасное изменение нативного состояния, которым владеет текущая print-generation. Если для раскрытия требуется реальное действие приложения, используется явное действие пользователя или безопасная альтернативная репрезентация.
4. Cleanup временного состояния не должен перезаписывать более новые изменения host page.

## PDF

1. На первом этапе обязательный способ сохранения — PDF.
2. PDF должен содержать выбранный контент целиком, кроме явных областей «Исключены».
3. Все ссылки исходной страницы внутри выбранного контента должны оставаться кликабельными.
4. Изображения также должны сохранять возможность перехода:
   - если изображение уже внутри ссылки — сохранить исходную ссылку;
   - если обычное изображение — сделать его ссылкой на исходный URL изображения.
5. В начале PDF разместить:
   - адрес сайта;
   - полный URL страницы, кликабельный;
   - Название страницы (значение HTML Title);
   - локальную дату и время формирования копии.
6. Желательно использовать печатный PDF, а не растр всей страницы, чтобы текст и ссылки сохранялись функциональными.

### Ресурсы перед PDF — P1-003

1. Перед печатью WebClip должен bounded-попытаться загрузить ресурсы, уже относящиеся к выбранному контенту: lazy images (`loading=lazy`, `data-src`, `data-srcset`), CSS background images и используемые web fonts.
2. Подготовка ресурсов не должна зависать: общий deadline — порядка 15 секунд, число resource tasks ограничено примерно 500; параллелизм также должен быть ограничен.
3. Нельзя превращать эту функцию в произвольный extension-level crawler/fetcher: не запрашивать URL, которых нет в выбранном DOM/CSS, и не читать сетевые response bytes расширением.
4. Временные изменения lazy-атрибутов принадлежат конкретной print-generation и после PDF восстанавливаются только compare-before-restore: если host page уже изменила тот же атрибут, WebClip не перезаписывает новое значение старым snapshot.
5. Если часть ресурсов не загрузилась, PDF всё равно формируется, а bounded-отчёт должен сохраняться вместе с записью Journal, отображаться в PDF metadata/header и быть доступен в OperationLog diagnostics.
6. Диагностика ресурсов не должна сохранять query/hash signed/tokenized URL; `data:`/`blob:` URL должны отображаться только как безопасные opaque labels.

## Имя файла

Актуальное правило:

`Название страницы (HTML Title) + имя сайта до третьего уровня домена + дата/время создания + расширение`

Дополнительные требования:

- полное имя вместе с `.pdf` не больше 100 символов;
- домен до третьего уровня и дата/время должны присутствовать;
- при превышении лимита в первую очередь обрезается Title;
- в имени не должно быть запрещённых символов;
- точка должна использоваться только для отделения имени от расширения;
- для локального скачивания и Яндекс Диска сейчас используется одно правило имени;
- каждое новое сохранение из журнала получает новое имя с новой датой/временем.

## Яндекс Диск

1. После «Готово» должно быть минимум два варианта:
   - Скачать PDF;
   - Отправить на Яндекс Диск.
2. Нужны настройки Яндекс Диска.
3. Пользователь должен выбрать корневую папку.
4. Внутри неё автоматически создаётся вложенность по имени сайта до третьего доменного уровня.
5. После отправки показать информационное окно об успехе либо ошибке.
6. Ошибка должна визуально отличаться от успеха и явно показывать, что ситуация требует разбора пользователем.
7. При ошибке области «Включены/Исключены» не очищать.
8. При ошибке пользователь должен иметь возможность:
   - повторить отправку;
   - открыть настройки;
   - скачать тот же PDF локально;
   - вернуться к выделению.
9. После ошибки повторная отправка не должна повторно формировать PDF — должен использоваться уже сформированный файл.
10. Фиксированный Redirect URI Яндекс OAuth должен использоваться как есть:
    `https://oauth.yandex.ru/verification_code`.
11. В расширении должна быть отдельная подробная инструкция по авторизации Яндекс, вызываемая отдельной кнопкой.

## Журнал

1. Добавить журнал сохранённых/отправленных файлов.
2. Для каждой операции сохранить информацию о том, какие области были «Включены» и какие «Исключены».
3. Просмотр журнала доступен через основную иконку расширения.
4. Режимы просмотра:
   - весь журнал;
   - журнал текущего URL;
   - журнал текущего сайта, нормализованного до третьего уровня домена.
5. Во время начала/режима выделения также должна быть возможность открыть журнал и выбрать предыдущие настройки областей «Включены/Исключены».
6. Применение старого шаблона не должно использовать старое имя файла; имя всегда формируется заново.
7. Изначально пользователь предложил хранить журнал в папке расширения. Ограничение Chrome не позволяет надёжно писать runtime-данные в каталог установленного расширения, поэтому согласованная техническая реализация — IndexedDB расширения.

## Версия

Номер версии должен отображаться в интерфейсе и автоматически браться из `manifest.json`, а не дублироваться вручную.

## Recovery / восстановление проекта — актуальное Git-first правило

1. Canonical WIP snapshot проекта — точный commit SHA в GitHub `main`; dated handoff/embedded archive не является источником истины.
2. Перед анализом или записью всегда fresh-fetch текущего `main`.
3. Для релиза точный tested commit фиксируется annotated release tag; пользовательский extension ZIP строится из этого commit/tag.
4. Вкладывать полный recovery/source ZIP внутрь каждой пользовательской сборки **не требуется** — прежнее правило superseded как P0-019.
5. При необходимости offline/disaster recovery создаётся отдельный recovery ZIP только из clean exact commit. Его metadata фиксирует source commit/tag, а manifest — SHA-256 файлов; dirty tree должен быть отвергнут builder-ом.
6. Актуальные research/status/evidence документы хранятся в Git и остаются синхронизированы с текущим `main`; исторические версии сохраняет Git history.

## Frame-aware страницы и iframe

1. Страницы, где основной документ находится в same-origin iframe (пример: 1С:ИТС), должны корректно выделяться.
2. «Основной контент» должен анализировать как верхний document, так и доступные iframe.
3. области «Включены/Исключены» и journal snapshot должны учитывать frame, чтобы восстановление работало внутри встроенного документа.
4. При печати длинный iframe-контент не должен теряться из-за фиксированной высоты/scroll-контейнера; расширение должно максимально раскрывать доступный печатный контент.
5. Cross-origin iframe не должен обходить Same-Origin Policy. Доступ к его DOM допускается только через content/frame agent, исполняющийся внутри frame после host permission, явно подтверждённого пользователем в Chrome.
6. Без host permission поведение остаётся прежним: top page и same-origin iframe работают, cross-origin DOM не читается.
7. Идентичность cross-origin frame должна определяться однозначно; при нескольких подходящих iframe восстановление/активация fail-closed, а не выбирает frame эвристически.

## Экспорт/импорт и очистка журнала

1. Полный журнал можно экспортировать во внешний JSON-файл через стандартную загрузку Chrome.
2. Один файл экспорта должен содержать всю информацию для полного восстановления журнала, включая области «Включены/Исключены» и frame path.
3. Полный журнал можно импортировать из такого файла; импорт заменяет текущий журнал.
4. Можно очистить весь журнал для сайта, нормализованного до третьего уровня домена.
5. Импорт, очистка всего журнала и очистка журнала домена требуют подтверждения специальным случайным 9-значным кодом, который пользователь должен прочитать и вручную ввести.
6. Для удаления одной отдельной строки достаточно обычного окна подтверждения.

## Резервная копия журнала на Яндекс Диске

1. Сам журнал всегда остаётся локальным; Яндекс Диск используется только для восстановления.
2. Пользователь НЕ выбирает отдельную папку журнала.
3. В выбранной корневой папке WebClipper сам поддерживает:
   - `Upload` — PDF страниц;
   - `Backup` — резервные копии;
   - `Backup/Journal` — журнал.
4. Каждая резервная копия журнала — новый полный JSON-файл. Предыдущие файлы не удаляются и не перезаписываются.
5. Внутри `Backup/Journal` автоматически создаются подпапки `MM-YYYY`, где `MM` — месяц с ведущим нулём, `YYYY` — год локального времени компьютера.
6. Имя версии содержит локальные дату и время создания, например `WebClip_Journal_2026-08-23_18-53-10-123.json`; upload выполняется с `overwrite=false`.
7. Папки проверяются перед операцией и автоматически создаются; невозможность создать их должна быть явной ошибкой.
8. Для фонового экспорта `Backup/Journal/MM-YYYY` также проверяются/создаются автоматически.
9. При импорте с Яндекс Диска сначала показывать отдельное окно со списком конкретных резервных файлов; пользователь явно выбирает файл. Автоматически выбирать последнюю копию запрещено.
10. После выбора файла показать стандартное опасное подтверждение с 9-значным кодом перед replace локального журнала.
11. При ручном экспорте на Яндекс Диск на странице показывать блокирующее окно прогресса с расшифровкой этапов. Пока операция не завершена, окно нельзя закрыть, а вкладка должна использовать `beforeunload`-защиту от случайного закрытия.
12. В настройках можно включить фоновый экспорт, задать обычный период в минутах (по умолчанию 1440 = 24 часа) и отдельный период повтора после ошибки, также в минутах.
13. Если срок пропущен из-за закрытого Chrome/недоступности, операция должна выполняться при первой возможности.
14. После фоновой ошибки повторять через настроенный retry-интервал.
15. В основном popup показывать отдельно время последней успешной и последней неудачной фоновой попытки и текущую проблему.

## Контекстное меню

Основной функционал WebClipper должен быть доступен из контекстного меню страницы. Контекстное меню обязано вызывать те же обработчики, что popup/toolbar, чтобы логика не расходилась.


## Дополнения 0.9.3

### Индикатор текущего URL
1. Если точный URL ранее успешно сохранялся, иконка на панели Chrome должна менять цвет по возрасту последнего успешного сохранения:
   - зелёный: ≤24 часов;
   - оранжевый: >24 часов и ≤30 дней;
   - красный: >30 дней.
2. Badge показывает количество уникальных локальных календарных дней с успешными копиями данного URL.
3. Несколько успешных копий одного URL в один день считаются одним днём.
4. Неуспешная отправка на Яндекс Диск и только временный retry-кэш не увеличивают счётчик.

### Контекстное меню
1. Перед раскрывающимся меню WebClipper должна находиться отдельная команда `Начать выделение WebClipper`.
2. Она использует ту же selection model, что и основной интерфейс.

### Импорт backup
1. При импорте с Яндекс Диска сначала показывать только файлы из текущего `MM-YYYY`.
2. Должна быть навигация по месяцам назад/вперёд.
3. При смене месяца отображается новый список только из выбранной месячной папки.
4. Будущие месяцы выбирать не требуется.

### Общий журнал и домены
1. В общем журнале нужен иерархический фильтр:
   - Все позиции;
   - домен базового/второго уровня вида `aaa.com`;
   - вложенный домен третьего уровня вида `bbb.aaa.com`.
2. Записи внутри любой выбранной группы показываются от новых к старым.
3. Для успешных Yandex-upload открытие сохранённого PDF выполняется нажатием на существующий badge/кнопку `Яндекс Диск` в карточке записи.
4. Отдельный элемент/ссылка `Открыть сохранённый файл на Яндекс Диске` в карточке не показывается.

### Ссылка Яндекс Диска
1. Предпочтительна ссылка, не построенная из имени/пути файла, поскольку файл может быть переименован или перемещён.
2. Техническая реализация: сохранить `public_url` опубликованного ресурса Яндекс Диска.
3. Пользователь должен иметь настройку управления созданием таких постоянных ссылок.
4. Нужно явно предупреждать, что опубликованный ресурс доступен владельцу ссылки.
5. В журнале отдельная текстовая ссылка `Открыть сохранённый файл на Яндекс Диске` удаляется.
6. Существующий badge/кнопка `Яндекс Диск` у записи становится кликабельным и открывает сохранённый файл по `publicUrl`, сохраняя текущий внешний вид.
7. Если у записи нет валидного `publicUrl`, интерфейс не должен имитировать доступное открытие файла; требуется понятное недоступное состояние/подсказка.

### Прогресс обычной отправки страницы
1. При формировании и отправке PDF страницы на Яндекс Диск на самой странице показывать progress UI.
2. Progress должен расшифровывать этапы формирования PDF и сетевой загрузки.
3. Пока операция выполняется, пользователь не должен случайно закрыть модальное окно или изменить selection state.
4. На попытку закрыть/перезагрузить вкладку использовать доступную браузеру `beforeunload`-защиту.
5. Служебный progress UI не должен попадать в сформированный PDF.


## Дополнения 0.9.4

### Индикатор успешных выгрузок
1. Цвет и badge иконки текущего URL должны учитывать **только факт полностью завершённой успешной выгрузки PDF на Яндекс Диск**.
2. До завершения upload + проверки результата операция в статистику не входит.
3. Локальное `Скачать PDF` не влияет на цвет и badge иконки.
4. Несколько успешных Yandex-upload одного URL в один локальный календарный день считаются одним днём.

### Режим записи журнала
1. Локальное формирование/скачивание PDF всегда остаётся в журнале.
2. Для каждой строки явно показывать режим: `Файл` или `Яндекс Диск`.
3. Старые записи определяются по уже существующему полю `destination`; миграция IndexedDB не требуется.

### Навигация журнала
1. В зависимости от режима просмотра должна быть визуально выделена ровно одна кнопка: `Текущий URL`, `Текущий сайт` или `Весь журнал`.
2. Открытый журнал должен автоматически видеть новые успешные операции без необходимости открывать новую вкладку Chrome.
3. При наличии `sourceTabId` журнал должен уточнять исходный URL по этой вкладке при загрузке.
4. Если журнал открыт с HTTP(S)-страницы, исходный URL/site context должен сохраняться при переходе в отдельную вкладку, чтобы из уже открытого журнала можно было переключаться между всеми тремя видами.
5. `Весь журнал` при наличии такого context всё равно не должен фильтроваться по исходному URL или сайту: context используется только для доступности последующего переключения.

### Фильтр доменов общего журнала
1. Сам блок фильтра общего журнала закрыт по умолчанию.
2. Каждый домен базового/второго уровня с вложенными третьими уровнями также закрыт по умолчанию и раскрывается отдельно пользователем.
3. Добавить поиск по домену. Поиск должен находить как базовые, так и третьи уровни и показывать только совпадающие ветки.
4. Порядок доменных групп сохраняется по дате самой новой записи: наиболее свежие сверху; записи внутри выбранной группы — новые сверху.

### Универсальный текстовый фильтр журнала
1. Фильтр состоит из нескольких строк условий; одновременно поддерживается до 8 строк.
2. Для каждой строки пользователь вводит отдельный текст и выбирает поля поиска: `Наименование`, `Комментарии`, `Сайт`, `URL`.
3. `Наименование` включено для новой строки по умолчанию; строка не должна оставаться без выбранного поля.
4. Непустые строки объединяются логикой `И` по умолчанию либо `ИЛИ` по выбору пользователя.
5. Фильтр накладывается поверх режима чтения, current/site/all и доменного фильтра и обязан применяться до подсчётов, URL-группировки и пагинации.
6. `Комментарии` включают комментарий к файлу и пользовательские комментарии записи журнала.
7. Фильтрация большого журнала не должна материализовать весь IndexedDB store в массив; применяется существующая bounded cursor/deadline архитектура.

## Дополнения 0.9.5

- Открытая страница журнала должна отражать новые записи без необходимости открывать вторую вкладку.
- После обновления/перезагрузки расширения ранее открытая страница журнала не должна молча оставаться в устаревшем состоянии: она должна автоматически перезагрузиться либо явно потребовать перезагрузку.

## Journal visibility reliability
- The full journal must show the same persistent entries regardless of which existing browser tab was used to open it.
- Opening the journal from a newly created Chrome tab must not be required to make entries visible.
- An already open visible journal should reflect newly committed entries automatically.

## Независимость полного журнала от активной вкладки

- `Весь журнал` должен показывать один и тот же полный набор локальных записей независимо от того, какая вкладка была активной при его открытии.
- В частности, результат не должен отличаться между `chrome://newtab/` и обычной `http(s)` страницей.
- Переход ранее пустой вкладки на URL не должен влиять на содержимое полного журнала.
- Контекст активной вкладки допускается использовать только для режимов `Текущий URL`, `Текущий сайт` и применения сохранённых областей «Включены/Исключены».


## Терминология и отображение областей страницы — P1-026

1. В карточке записи журнала убрать отдельную информационную строку вида `Сохранено областей: 1 · Исключено: 0`, поскольку эти количества уже отображаются в заголовке блока областей.
2. Заголовок блока `Области страницы Включены/Исключены` переименовать в `Области страницы Включены/Исключены`.
3. Во всех пользовательских интерфейсах, сообщениях, подсказках и документации, где речь идёт о выбранных/исключённых областях страницы, использовать русские термины `Включены` и `Исключены`; внутренние поля `includes`/`excludes` остаются техническими и не показываются пользователю.
4. Это требование относится к пользовательскому представлению. Внутренние совместимые поля данных (`includes`, `excludes` и аналогичные технические идентификаторы) не требуется переименовывать, если это создаёт риск миграции или несовместимости.
5. Счётчики включённых и исключённых областей должны остаться доступны в заголовке блока и не дублироваться отдельной строкой.

## Удаление отдельных записей и файлов Яндекс Диска — 0.9.8

1. Для записи `destination=yandex` кнопка «Удалить запись» должна требовать выбор одного из двух вариантов; удаление без выбора запрещено.
2. Вариант «Оставить файл на Яндекс Диске» удаляет только запись журнала.
3. Вариант «Так же удалить файл на Яндекс Диске» не уничтожает файл физически, а переносит его в `<root>/Trash/MM-YYYY`.
4. `MM-YYYY` определяется по локальной дате фактического удаления, с ведущим нулём месяца.
5. Сначала должен успешно завершиться move на Яндекс Диске, после чего удаляется локальная запись. При ошибке move запись остаётся.
6. Если пользователь переименовал или переместил файл после сохранения, WebClip должен по возможности найти актуальный ресурс не только по старому path.
7. Для локального режима `destination=download` удаляется только journal entry; локально скачанный PDF автоматически не удаляется.
8. Для новых Yandex-записей Journal должен сохранять locator context `accountUid`, `rootPath`, `resourceId`, `publicUrl`, `remotePath`; export/import сохраняет эти поля.
9. Если сохранённый `accountUid` не совпадает с текущим аккаунтом либо сохранённый `rootPath` не совпадает с выбранным root, destructive remote action должна завершаться fail-closed до изменения файла/записи.
10. Если у записи известен `resourceId`, совпадение только по старому path недостаточно. Точный `publicUrl` может использоваться как secondary identity только при отсутствии `resource_id` у кандидата; конфликтующий `resourceId` имеет приоритет и запрещает match.
11. Старые записи без `accountUid/rootPath/resourceId` остаются совместимыми с существующим managed-path fallback; shared delete→Trash flow без отдельного repro не перерабатывается.


## Отображение способа сохранения и статуса чтения — P1-027

1. В карточке записи журнала убрать отдельную информационную строку вида `Режим выгрузки: Яндекс Диск · Статус чтения: Прочитать позже` и аналогичные варианты.
2. Способ сохранения показывается только отдельным badge в верхней группе статусов записи:
   - для `destination=yandex` — существующий badge `Яндекс Диск`;
   - для `destination=download` — badge `Скачан локально`.
3. Badge `Скачан локально` должен быть визуально нейтральным, в чёрно-белой/серой цветовой гамме, чтобы не смешиваться с цветовым смыслом badge `Яндекс Диск`.
4. Статус чтения продолжает показываться отдельным badge `Прочитано` или `Прочитать позже`; отдельная текстовая строка статуса чтения не дублируется.
5. Badge способа сохранения и badge статуса чтения всегда располагаются горизонтально в одной группе без переноса друг под друга при штатной ширине карточки.
6. Для старых записей способ отображения определяется по существующему полю `destination`; миграция IndexedDB только ради этой UI-правки не требуется.
7. Для локально скачанного PDF badge `Скачан локально` является информационным и не должен имитировать открытие локального файла, если Chrome не предоставляет устойчивой ссылки/handle на скачанный файл.

## Размещение badge способа сохранения и статуса чтения — P1-028

1. В карточке записи журнала badge способа сохранения (`Яндекс Диск` либо `Скачан локально`) и badge статуса чтения (`Прочитано` либо `Прочитать позже`) убрать из правого верхнего блока карточки.
2. Оба badge разместить непосредственно под названием страницы, в той же строке, где выводятся дата и время записи.
3. Дата и время остаются слева; группа badge располагается справа от даты и времени.
4. Текущие габариты, внутренние отступы, высота и визуальная плотность переносимых badge не изменяются только из-за переноса.
5. Badge способа сохранения и badge статуса чтения должны оставаться горизонтально рядом друг с другом и не переноситься друг под друга при штатной ширине карточки.
6. Перенос не должен менять семантику существующих badge: `Яндекс Диск` остаётся действием открытия сохранённого Yandex-файла согласно P1-025, `Скачан локально` остаётся информационным согласно P1-027.
7. Правый верхний блок после переноса не должен оставлять пустой визуальный контейнер/зарезервированное место.


## Экспорт и импорт пользовательских настроек — P1-008

1. Пользователь должен иметь возможность перенести настройки WebClip между профилями/браузерами отдельным JSON-файлом.
2. Формат: `webclip-user-settings` version 1.
3. Экспортируются только пользовательские настройки: Yandex `clientId`, `rootPath`, `createPublicLinks`, параметры фонового backup; настройка Journal `groupByUrl`; срок хранения OperationLog.
4. OAuth access token, refresh token, Client Secret, PKCE state/code verifier, verification code, session auth, Journal entries, durable checkpoints, состояние backup-операций и содержимое OperationLog не должны попадать в файл.
5. Импорт не должен отключать, заменять или изменять текущую OAuth-сессию.
6. Перед записью файл должен полностью пройти bounded size/schema/type validation; неизвестные или секретные поля отклоняются fail-closed.
7. Настройки должны применяться одной bundled storage-операцией. При неизвестном settlement Chrome API WebClip не должен автоматически повторять импорт; служебный scheduler reconciliation должен быть восстановим после перезапуска MV3 worker.
