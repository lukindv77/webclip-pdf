# Текущие требования и технические условия — WebClip PDF

Status: **CANONICAL CURRENT BASELINE**

Этот документ фиксирует **только действующие на текущий момент требования и технические условия** проекта WebClip PDF. Он не является журналом изменения требований и не должен содержать цепочку «сначала было так → затем изменили».

Для ответа на вопрос «что требуется сейчас» используется этот файл и текущие canonical contracts проекта. Для ответа на вопрос «почему принято именно так» используется `DECISIONS_AND_RATIONALE.md`. Историческая эволюция требований сохраняется в Git history и не должна собираться заново при обычной разработке или **Комплексном исследовании, оценке и проработке проекта и его архитектуры**.

Если исторический документ, старый commit, handoff, research evidence или release note противоречит этому current baseline, он не изменяет текущее требование без отдельного нового принятого решения, интегрированного в `main`.

## 1. Назначение и главный продуктовый результат

WebClip PDF — Chrome Extension Manifest V3 для выборочного WebClipping веб-страниц с основным форматом сохранения PDF.

Главная цель: пользователь должен иметь возможность явно определить нужное содержимое страницы и получить максимально точную, пригодную для чтения и архивного хранения копию именно выбранного состояния страницы, насколько это безопасно и технически представимо текущим PDF-режимом.

Технический успех API-вызова, скачивания или наличия PDF-файла сам по себе не считается достаточным, если сохранённый результат не соответствует пользовательскому намерению и фактическому состоянию выбранного содержимого.

**Почему:** продукт ценен точностью архивной копии, а не только фактом создания файла.

## 2. Выделение областей страницы

1. Пользователь может выбрать одну или несколько областей «Включены».
2. Пользователь может явно создать вложенные области «Исключены».
3. Более крупная новая область «Включены» может поглотить ранее выбранные дочерние области «Включены».
4. Валидные области «Исключены» сохраняются при таком укрупнении, если остаются внутри выбранного родителя.
5. В область «Включены» входит её выбранное DOM-поддерево с дочерними элементами, кроме явно исключённых поддеревьев.
6. Области могут быть смежными и принадлежать одному родителю.
7. Пользовательский интерфейс использует термины `Включены` и `Исключены`; внутренние совместимые поля `includes`/`excludes` могут сохраняться.
8. «Основной контент» должен выбирать типовую область-кандидат, после чего пользователь может вручную добавлять/изменять области.
9. WebClip не должен автоматически исключать контент, который он эвристически считает рекламой.
10. «Найти рекламу» допускается только как подсветка/предложение кандидатов; окончательное исключение делает пользователь.
11. Счётчики включённых и исключённых областей показываются без дублирующей информационной строки в карточке Journal.

**Почему:** модель «Включены/Исключены» позволяет сохранять крупный логический блок и безопасно вырезать только явно нежелательные вложенные части, не передавая эвристике право необратимо менять пользовательский выбор.

## 3. Frame-aware selection и identity

1. Same-origin `iframe/frame` являются полноценными selection scopes.
2. «Основной контент» анализирует top document и доступные same-origin frames.
3. Selection snapshot хранит frame identity вместе с локатором элемента, чтобы восстановление работало внутри встроенного документа.
4. Длинный iframe-контент не должен теряться только из-за текущей фиксированной высоты/scroll container.
5. Cross-origin DOM не обходится через нарушение Same-Origin Policy.
6. Доступ к cross-origin frame допускается только через permission-gated frame agent после явного пользовательского предоставления соответствующего host permission в Chrome.
7. При отсутствии permission top page и same-origin frames продолжают работать, а cross-origin DOM остаётся недоступным.
8. Frame/document identity должна разрешаться однозначно; при неоднозначности восстановление/активация завершается fail-closed, а не выбирает frame эвристически.
9. Navigation/reload/document replacement не должны молча применять selection state к другой логической document generation.

**Почему:** fidelity требует связывать пользовательский выбор с конкретным документом/frame, не расширяя полномочия расширения за пределы браузерной permission model.

## 4. Скрытый и сворачиваемый контент

1. Полезный скрытый контент внутри выбранной области следует включать в статическую PDF-копию там, где это можно сделать без выполнения произвольной бизнес-логики страницы.
2. WebClip не получает право synthetic-click произвольные `button`, link, submit, accordion/toggle controls либо выполнять navigation/submit/application side effects ради печати.
3. Допустимы inert/static representation и безопасное изменение нативного состояния, которым владеет текущая print-generation.
4. Если раскрытие требует реального действия приложения, необходим явный пользовательский шаг либо безопасная альтернативная статическая репрезентация.
5. Cleanup временного состояния не должен перезаписывать более новые изменения host page.

**Почему:** архивная полнота не должна достигаться ценой исполнения page-owned действий с непредсказуемыми side effects.

## 5. PDF и fidelity

1. Основной текущий формат сохранения — печатный PDF через Chromium `Page.printToPDF`, а не raster screenshot всей страницы.
2. PDF должен содержать выбранное содержимое полностью в пределах действующего fidelity contract, кроме явных областей «Исключены».
3. Текст должен по возможности оставаться текстом.
4. Ссылки исходной страницы внутри выбранного контента должны оставаться кликабельными, если Chromium способен представить их как безопасные PDF annotations.
5. Если изображение уже находится внутри ссылки, сохраняется исходная ссылка.
6. Если обычное изображение не находится внутри ссылки, печатное представление должно сохранять возможность перейти к исходному URL изображения, если это безопасно и доступно.
7. В начале PDF должны присутствовать:
   - адрес сайта;
   - полный URL страницы как кликабельная ссылка;
   - `Название страницы` из HTML Title;
   - локальная дата и время формирования копии.
8. Служебный UI самого расширения не должен попадать в PDF.
9. Responsive/resource/temporal/frame state сохранённой копии должен относиться к той же admitted logical document generation, что и пользовательский выбор, либо результат должен честно классифицироваться как degraded/unknown/failure вместо ложного success.
10. Точный текущий fidelity/completeness contract задаёт `WEBCLIP_PDF_FIDELITY_CONTRACT.md`.

**Почему:** печатный DOM/PDF сохраняет текст, ссылки и структуру лучше полного растра, но требует строгой связи между выбранным состоянием и финальным render cut.

## 6. Подготовка ресурсов перед PDF

1. Перед печатью WebClip bounded-пытается подготовить ресурсы уже относящиеся к выбранному DOM/CSS:
   - lazy images;
   - `data-src` / `data-srcset`;
   - CSS background images;
   - используемые web fonts.
2. Подготовка не превращается в произвольный extension-level crawler/fetcher: расширение не запрашивает новые URL вне selected DOM/CSS и не читает сетевые response bytes только ради этой функции.
3. Действующие пределы:
   - общий deadline около 15 секунд;
   - максимум около 500 resource tasks;
   - ограниченный concurrency;
   - bounded scan и per-item wait.
4. Временные изменения lazy-атрибутов принадлежат конкретной print-generation и восстанавливаются compare-before-restore.
5. Ошибка части ресурсов не обязана отменять формирование PDF, но должна быть отражена в bounded diagnostics/resource report.
6. Persisted diagnostics не должны сохранять query/hash signed/tokenized URL; `data:`/`blob:` обозначаются безопасными opaque labels.

**Почему:** подготовка повышает completeness, но должна оставаться ограниченной по времени/объёму и не расширять сетевой trust boundary.

## 7. Имя PDF

Текущее правило имени:

`Название страницы (HTML Title) + домен до третьего уровня + локальная дата/время + .pdf`

Требования:

- полное имя вместе с `.pdf` — не более 100 символов;
- домен и дата/время обязательны;
- при превышении лимита в первую очередь сокращается Title;
- запрещённые для имени файла символы удаляются/нормализуются;
- точка используется только для отделения расширения;
- локальное скачивание и Яндекс Диск используют одно правило;
- новое сохранение из Journal получает новое имя с новым временем, а не копирует старое имя.

**Почему:** имя должно быть переносимым, ограниченным по длине и одновременно позволять понять источник и время сохранения.

## 8. Яндекс Диск

1. После подготовки пользователь должен иметь минимум два действия:
   - скачать PDF локально;
   - отправить PDF на Яндекс Диск.
2. Пользователь задаёт один `rootPath`.
3. WebClip владеет служебной структурой внутри root, включая `Upload` и `Backup/Journal`.
4. Папки проверяются перед операцией и при необходимости создаются; невозможность создать требуемую папку является явной ошибкой.
5. Ошибка Yandex-операции визуально отличается от успеха и явно требует решения пользователя.
6. После ошибки области «Включены/Исключены» не очищаются.
7. Пользователь может повторить отправку, открыть настройки, скачать тот же PDF локально либо вернуться к выделению.
8. Retry после ошибки использует те же operation-owned PDF bytes и не вызывает новый `printToPDF`.
9. OAuth использует Authorization Code + PKCE и фиксированный Redirect URI `https://oauth.yandex.ru/verification_code`.
10. Client Secret не хранится в Chrome Extension.
11. В расширении должна быть отдельная подробная инструкция по Yandex OAuth.
12. При включённой настройке WebClip может публиковать загруженный ресурс и сохранять `publicUrl`; пользователь должен быть предупреждён, что опубликованный ресурс доступен владельцу ссылки.
13. Journal не строит устойчивую ссылку на файл только из имени/пути, поскольку пользователь может переместить или переименовать ресурс.
14. Обычная отправка страницы показывает поэтапный progress UI; во время критической операции UI не должен позволять случайно изменить selection state, а доступная браузеру `beforeunload`-защита используется от случайного закрытия/перезагрузки.
15. Progress UI временно исключается из render cut и не попадает в PDF.

**Почему:** remote storage является внешней boundary, поэтому операция должна быть повторяемой по тем же байтам, иметь понятное recovery-поведение и устойчивую identity/ссылку.

## 9. Локальный Journal

1. Рабочий Journal хранится локально в IndexedDB; Яндекс Диск не является рабочей базой Journal.
2. В Journal сохраняются локальные PDF-операции и Yandex-операции.
3. Для записи сохраняется selection snapshot областей «Включены/Исключены» и frame identity.
4. Основные виды:
   - `Текущий URL`;
   - `Текущий сайт`;
   - `Весь журнал`.
5. `Весь журнал` показывает один и тот же persistent dataset независимо от активной вкладки, origin страницы, `chrome://newtab/` или последующей навигации вкладки.
6. Source-page context допускается только для URL/site views и применения selection snapshot.
7. Уже открытая видимая страница Journal должна отражать новые committed entries без необходимости открывать вторую вкладку.
8. После reload/update расширения ранее открытая Journal page не должна молча оставаться устаревшей: она должна восстановиться либо явно потребовать reload.
9. При наличии исходного HTTP(S) context пользователь из уже открытого Journal может переключаться между URL/site/all views; `Весь журнал` при этом не фильтруется исходным context.
10. Selection snapshot можно применять к тому же URL либо совместимой странице того же сайта; результат требует проверки, потому что DOM может измениться.
11. Применение старого snapshot не наследует старое имя PDF.
12. Мутации Journal централизованы в privileged runtime layer, а чтение должно соблюдать bounded/paged/deadline архитектуру.

**Почему:** Journal является локальной durable памятью пользователя и не должен менять содержимое в зависимости от случайного browser-tab context.

## 10. Фильтры, группировка и отображение Journal

1. Общий Journal имеет иерархический фильтр:
   - все позиции;
   - базовый/второй уровень домена;
   - третий уровень домена.
2. Доменный блок и вложенные доменные группы закрыты по умолчанию и раскрываются пользователем.
3. Поиск по домену показывает только совпадающие ветки.
4. Группы сортируются по самой новой записи; записи внутри группы — новые сверху.
5. Универсальный текстовый фильтр поддерживает до 8 строк.
6. В строке выбираются поля `Наименование`, `Комментарии`, `Сайт`, `URL`; `Наименование` включено по умолчанию.
7. Непустые строки объединяются `И` по умолчанию либо `ИЛИ` по выбору пользователя.
8. Фильтрация применяется до подсчётов, URL-группировки и пагинации и не должна материализовать весь IndexedDB store в один массив.
9. В карточке способ сохранения показывается только badge:
   - `Яндекс Диск`;
   - `Скачан локально`.
10. Статус чтения показывается только badge `Прочитано` / `Прочитать позже`.
11. Способ сохранения и статус чтения не дублируются отдельной текстовой строкой.
12. Эти badges располагаются под названием страницы в строке даты/времени: дата/время слева, badge-группа справа; при штатной ширине badges остаются рядом.
13. `Яндекс Диск` открывает сохранённый ресурс по валидному `publicUrl`; если устойчивой ссылки нет, UI показывает недоступное состояние и не имитирует рабочее действие.
14. `Скачан локально` информационный и не имитирует открытие локального файла без устойчивого browser handle/link.

**Почему:** Journal должен оставаться однозначным и масштабируемым при большом объёме данных без дублирования статусов и unbounded materialization.

## 11. Индикатор текущего URL

1. Иконка/badge текущего URL учитывают только полностью завершённые успешные Yandex uploads PDF.
2. Локальное скачивание не влияет на индикатор.
3. Цвет отражает возраст последней успешной remote-копии точного URL:
   - зелёный: до 24 часов включительно;
   - оранжевый: более 24 часов и до 30 дней включительно;
   - красный: более 30 дней.
4. Badge показывает число уникальных локальных календарных дней с успешными Yandex uploads точного URL.
5. Несколько успешных upload одного URL в один локальный календарный день считаются одним днём.
6. Failed/unknown/retry-only операции не увеличивают счётчик.

**Почему:** индикатор должен означать подтверждённое наличие удалённой архивной копии, а не локальную попытку или промежуточное состояние.

## 12. Экспорт, импорт и опасные операции Journal

1. Полный Journal экспортируется в один JSON-файл, достаточный для восстановления поддерживаемых данных Journal, включая selection snapshot/frame identity.
2. Полный Journal можно импортировать; импорт заменяет локальный Journal только после полной проверки входного файла и подтверждения.
3. Импорт, очистка всего Journal и очистка Journal домена требуют случайного 9-значного кода, который пользователь читает и вводит вручную.
4. Удаление одной локальной записи требует обычного confirm.
5. Операции должны иметь bounded size/schema/count/deadline validation и fail-closed поведение при неизвестном settlement.

**Почему:** массовые необратимые изменения требуют более сильного пользовательского подтверждения и строгой admission-проверки.

## 13. Резервные копии Journal на Яндекс Диске

1. Remote backup используется для восстановления, а не как рабочая Journal database.
2. Путь: `<root>/Backup/Journal/MM-YYYY/`.
3. Каждый backup — новый полный JSON-файл; предыдущие версии не перезаписываются и не удаляются автоматически.
4. Имя содержит локальные дату/время; upload выполняется без overwrite.
5. При restore пользователь сначала выбирает месяц, затем конкретный backup-файл; автоматический выбор «последнего» запрещён.
6. После скачивания/валидации конкретного файла replace локального Journal требует 9-значного подтверждения.
7. Ручной backup показывает блокирующий поэтапный progress UI и использует `beforeunload` protection на время операции.
8. Background backup имеет normal interval и отдельный retry interval.
9. Пропущенный срок из-за закрытого Chrome выполняется при первой возможности.
10. После ошибки используется retry schedule.
11. Popup отдельно показывает последнюю успешную и последнюю неудачную фоновую попытку и текущую проблему.

**Почему:** versioned full snapshots дают понятную точку восстановления и не связывают доступность локального Journal с сетью.

## 14. Удаление Yandex-записи и remote file identity

1. Для `destination=yandex` удаление Journal entry требует выбрать:
   - оставить файл на Яндекс Диске;
   - переместить связанный файл в `<root>/Trash/MM-YYYY` и затем удалить Journal entry.
2. Remote delete-функция не выполняет физическое уничтожение файла; используется move в Trash.
3. `MM-YYYY` определяется по локальной дате фактического удаления.
4. Сначала должен успешно завершиться remote move, после чего удаляется локальная запись; при ошибке move запись остаётся.
5. Новые Yandex entries сохраняют locator context `accountUid`, `rootPath`, `resourceId`, `publicUrl`, `remotePath`; export/import сохраняет эти поля.
6. Destructive remote action fail-closed, если текущий account/root не совпадает с сохранённым context.
7. Если известен `resourceId`, совпадение только по старому path не считается достаточной identity.
8. `publicUrl` может использоваться как secondary identity только при отсутствии `resourceId` у кандидата; конфликтующий `resourceId` запрещает match.
9. Для legacy entries без полного locator context допускается только явно поддерживаемый managed-path fallback.
10. Для `destination=download` удаляется только Journal entry; локальный PDF автоматически не удаляется.

**Почему:** удалённый файл может быть переименован/перемещён, поэтому destructive action требует устойчивой resource/account/root identity и безопасного порядка side effects.

## 15. Перенос пользовательских настроек

1. Пользователь может экспортировать/импортировать настройки отдельным JSON-файлом формата `webclip-user-settings` version 1.
2. Экспортируются только явно разрешённые пользовательские настройки.
3. OAuth access/refresh tokens, Client Secret, PKCE/session secrets, Journal entries, durable operation checkpoints и OperationLog не экспортируются.
4. Импорт не отключает и не заменяет текущую OAuth-сессию.
5. До записи выполняется bounded size/schema/type/unknown-field/secret-field validation.
6. Настройки применяются одной bundled storage operation; неизвестный settlement не должен автоматически повторяться как новая запись, а reconciliation должен быть восстановим после MV3 worker restart.

**Почему:** перенос настроек должен быть удобным, не превращаясь в экспорт credential/session state и не создавая duplicate side effects при timeout.

## 16. Контекстное меню и точки входа

1. Основной функционал доступен из popup/toolbar и контекстного меню.
2. Перед раскрывающимся WebClip menu присутствует отдельная команда `Начать выделение WebClipper`.
3. Все entry points используют общую бизнес-логику/state machine и не содержат независимых расходящихся реализаций.

**Почему:** несколько UI entry points не должны порождать разные семантики одной операции.

## 17. Версия и release semantics

1. Версия, показываемая пользователю, берётся из `manifest.json`.
2. Docs/research commit сам по себе не повышает runtime version.
3. Manifest `0.9.8` остаётся текущей runtime version до отдельного release decision; `0.9.9` — WIP, а не released version.
4. Build/tag/GitHub Release создаются только после отдельного явного решения о релизе и выполнения применимых release gates.

**Почему:** source/research progression и официальный release — разные состояния.

## 18. Git-first recovery и current project baseline

1. Canonical WIP source snapshot — exact commit SHA свежего GitHub `main`.
2. Dated handoff, chat memory, generated ZIP и historical document не являются параллельным source of truth.
3. Выпущенная версия привязывается к exact tested commit и annotated release tag.
4. Пользовательский extension ZIP не обязан содержать вложенный полный recovery/source ZIP.
5. Отдельный offline/disaster recovery ZIP допускается только из clean exact commit с source metadata и SHA-256 manifest.
6. **Current requirements baseline** — этот файл.
7. **Current rationale/decision baseline** — `DECISIONS_AND_RATIONALE.md`.
8. Будущая разработка и **Комплексное исследование проекта** должны начинаться от этих current documents и fresh `main`, а не реконструировать действующие требования из цепочки прошлых изменений.
9. История требований и отменённых подходов сохраняется в Git history и извлекается только когда она действительно нужна для provenance, расследования regression или объяснения конкретного решения.

**Почему:** один нормализованный current baseline устраняет противоречия между накопленными редакциями и снижает риск вернуть отменённое требование.

## 19. Обязательные требования к Комплексному исследованию проекта

Каноническое понятие: **«Комплексное исследование, оценка и проработка проекта и его архитектуры»**.

Для каждого существенного исследуемого вопроса необходимо:

1. начинать с fresh `main` и current baseline проекта;
2. проверять текущий код/архитектуру/requirements/contracts;
3. выполнять внешнее исследование по множеству релевантных источников, включая по возможности:
   - официальные сайты и документацию аналогичных/смежных продуктов и вендоров;
   - похожие или частично смежные open-source проекты на GitHub и GitLab;
   - issues/discussions этих проектов;
   - стандарты, спецификации и browser/platform documentation;
   - дискуссионные форумы, Reddit и другие источники пользовательского опыта;
4. использовать внешние подходы как **гипотезы, known failure modes и варианты решения**, а не как автоматическое требование копировать чужую архитектуру;
5. сравнивать несколько независимых источников и учитывать применимость, trade-offs, product mission, безопасность, стоимость сложности, maintainability и фактическое состояние WebClip;
6. проверять итоговый вывод против fresh WebClip `main`;
7. при отсутствии достаточных внешних источников явно фиксировать границу поиска/неопределённость, а не подменять её одним случайным источником;
8. security-анализ выполнять только как defensive security / защитный архитектурный анализ.

**Почему:** внешняя практика расширяет пространство гипотез и известных failure modes, но решение должно быть самостоятельным и доказанным применительно к WebClip.

## 20. Актуальность проекта в GitHub

1. Перед каждой содержательной инструментальной сессией выполняется fresh-fetch `main` с exact HEAD SHA.
2. Перед записью, интеграцией и merge повторно проверяется актуальность relevant base/head.
3. Open PR, Issues и branches проверяются как возможное незавершённое durable state.
4. Принятые изменения требований, архитектуры, research status и project policy не должны оставаться только в чате: они синхронизируются с GitHub обычным PR-first процессом.
5. После merge canonical `main` и обязательный post-merge integrity state должны быть подтверждены до начала независимой следующей работы.
6. Если `main` изменился, предыдущий snapshot считается checkpoint, а не current truth.

**Почему:** GitHub `main` является единственным устойчивым текущим состоянием проекта, поэтому развитие по stale snapshot недопустимо.

## 21. Инструментальные сессии и разбиение исследования

1. Перед началом **Комплексного исследования проекта** оценивается объём работы, доступное инструментальное окно, требуемые external/physical gates и безопасные durable checkpoints.
2. Если весь планируемый объём нельзя качественно завершить в одном окне, работа заранее либо по фактической переоценке разбивается на несколько сессий/tranches.
3. Каждая часть должна оставлять точную durable resume point в GitHub.
4. Количество инструментальных окон не является метрикой успеха.
5. Приоритет: полнота, точность, глубина проверки деталей, корректная root-cause reconciliation и доказательность — выше стремления уложить исследование в минимальное число сессий.
6. Нельзя искусственно урезать scope или снижать evidence level только ради завершения в одном окне.

**Почему:** длинное исследование должно быть interruption-safe без компромисса по качеству.

## 22. Local-first и экономия GitHub Actions

1. Любые проверки, анализ, генерация fixture, deterministic tests, syntax/static checks и иные операции сначала выполняются доступными локальными/встроенными инструментами, если они способны честно подтвердить требуемое утверждение.
2. GitHub Actions не используется просто как удобный интерактивный debugger или замена доступной локальной проверке.
3. GitHub Actions применяется, когда:
   - требуемую среду/границу нельзя достоверно воспроизвести локально; либо
   - действие является обязательным canonical delivery/release gate проекта, включая exact-head и post-merge Repository Integrity.
4. Перед push следует устранять локально обнаруживаемые ошибки и по возможности собирать изменения в coherent checked head, уменьшая число runner-запусков.
5. Экономия Actions не может отменять physical Chrome/external verification, exact-SHA integrity, TOCTOU, post-merge validation или другой evidence layer, необходимый для правдивого вывода.

**Почему:** runner minutes следует расходовать на независимую/внешнюю проверку, а не на работу, которую можно надёжно выполнить без GitHub Actions.
